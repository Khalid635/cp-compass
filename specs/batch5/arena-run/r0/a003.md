# CP Compass PWA — service-worker caching design

## Governing idea

A library with a bank vault inside. The shell — `index.html`, JS/CSS, fonts, logo — is a reference book on open shelves: identical for every reader. Everything under `/api/v1` is a safe-deposit box: never photocopied, never left on a shelf, fetched fresh by its owner. Three breaks in the analogy, fixed here: (1) books keep their titles, but Vite renames hashed assets each build — the worker discovers them from the build manifest at install; (2) a library never shreds old editions — activation deletes every cache that is not the current build; (3) a vault visit can be slow (Render sleeps, ~50 s cold start) — the shell loads from the shelf while the backend wakes.

Assumptions: the manifest already exists (`CP Compass`, standalone, `start_url: "/"`); Vite has `build.manifest: true`, emitting `.vite/manifest.json`; `vite.config.ts` defines `__BUILD_ID__` as git short SHA or build timestamp.

## 1. Cache names and versioning

One cache only: `cp-shell-<BUILD_ID>`, e.g. `cp-shell-a3f9c1e`. A new deploy changes `BUILD_ID`, so the new worker installs into a brand-new empty cache and can never serve the previous build's files. On `activate` it deletes every cache starting `cp-shell-` that is not current.

## 2. Precache list (install)

Precached: `/`, `/index.html`, `/manifest.webmanifest`, `/compass.svg`, the `/fonts/*.woff2` files, plus every JS/CSS file in `/.vite/manifest.json`. If the manifest fetch fails, install still succeeds; missing assets arrive via runtime caching (§3). If a core file fails, `cache.addAll` rejects and the worker never activates — a broken deploy never replaces a working shell.

NOT precached: anything under `/api/v1` (including public `/demo/*`, §6), no hashed asset by literal name, any response with `Authorization`, `Set-Cookie`, or `private/no-store`, anything non-GET.

## 3. Fetch-handler routing

The worker calls `respondWith` only for same-origin `GET` requests with no `Authorization` header; everything else bypasses the worker entirely, adding zero latency.

| Request | Strategy | Why |
|---|---|---|
| `/api/v1/*`, incl. `/api/v1/sync/stream` (SSE) | **No handler — bypass** | Live private data; bypassing guarantees nothing is cached, no header inspected, the SSE stream never buffered. |
| Navigations | **Network-first, 4 s race, cached `index.html` fallback** | Online users get the newest `index.html` and hashed assets; the 4 s race means a sleeping Render backend never blocks the shell. |
| `/assets/*`, `/fonts/*`, `/compass.svg`, manifest, other same-origin static files | **Cache-first** | Asset filenames are content hashes — a URL's bytes never change. Stable files are versioned out by the cache name on deploy. |
| Cross-origin, POST/PUT/DELETE, any request with `Authorization` | **No handler — bypass** | The worker never sees, stores, or replays a token. It cannot read `localStorage` (workers have none). |

Only the cache-first branch ever calls `cache.put` — no code path can cache an `/api` response.

## 4. Update flow

1. The browser re-checks `/sw.js` on every navigation; a byte change installs a new worker in the background while the old one serves.
2. The new worker precaches the new shell, then waits. It never calls `skipWaiting()` alone — forced activation could interrupt a sync or lose form state.
3. `main.tsx` shows one toast when a worker is `waiting`: "New version available — Refresh". Tapping it posts `{ type: "SKIP_WAITING" }`; the worker activates, deletes old caches, claims clients, and the page reloads once.
4. Ignoring the toast still lands the update on the next full reload or when the last tab closes. No silent auto-reload; nobody stays on a stale shell.

## 5. Offline behaviour

After one online visit the shell loads fully offline. The router renders the requested route, including a deep link such as `/app/dashboard` — any navigation offline is answered with cached `/index.html`, and the SPA router takes over. On a data page the user sees the real shell with an explicit offline state and a retry button: "You're offline. Your dashboard needs a connection." No stale data is shown — none was cached — and none is invented. A first-ever visit while offline cannot work; the browser's standard offline page is the correct result.

## 6. What is NOT cached, and recovery from a buggy worker

Never cached: all `/api/v1` responses (dashboard, submissions, settings, sync status, SSE), all `/demo/*` even though public — one uniform rule, "no `/api` response is cached", means a future private route under `/api` cannot leak through a classification mistake — plus tokens and non-GET requests. Shared devices are safe: the only thing on disk after logout is the public shell, identical for every user. Logout needs no cache purge.

If the worker is buggy, recovery is a deploy, not a user action: ship a no-op `sw.js` whose `install` calls `skipWaiting()` and whose `activate` deletes every `cp-*` cache and unregisters the worker. That kill-switch reaches users through §4. Registration is production-only, so a bad worker never affects development.

## 7. Implementation

```js
const BUILD_ID = "__BUILD_ID__";
const CACHE = `cp-shell-${BUILD_ID}`;
const CORE = ["/", "/index.html", "/manifest.webmanifest", "/compass.svg",
  "/fonts/inter-400.woff2", "/fonts/inter-600.woff2"];
addEventListener("install", (e) => e.waitUntil((async () => {
  const cache = await caches.open(CACHE);
  const m = await fetch("/.vite/manifest.json").then((r) => r.json()).catch(() => ({}));
  const assets = Object.values(m).flatMap((v) => [v.file, ...(v.css || [])].map((a) => "/" + a));
  await cache.addAll([...CORE, ...assets]);
})()));
addEventListener("activate", (e) => e.waitUntil((async () => {
  for (const k of await caches.keys())
    if (k.startsWith("cp-shell-") && k !== CACHE) await caches.delete(k);
  await clients.claim();
})()));
addEventListener("message", (e) => {
  if (e.data?.type === "SKIP_WAITING") skipWaiting();
});
addEventListener("fetch", (e) => {
  const { request } = e, u = new URL(request.url);
  if (request.method !== "GET" || u.origin !== self.location.origin
      || request.headers.has("Authorization") || u.pathname.startsWith("/api/")) return;
  if (request.mode === "navigate") {
    e.respondWith((async () => {
      try { return await Promise.race([fetch(request),
        new Promise((_, rej) => setTimeout(rej, 4000))]); }
      catch { return caches.match("/index.html"); }
    })());
    return;
  }
  const put = (r) => { caches.open(CACHE).then((c) => c.put(request, r.clone())); return r; };
  e.respondWith(caches.match(request).then((h) => h || fetch(request).then(put)));
});
```

`main.tsx` (production only):

```ts
if (import.meta.env.PROD && "serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js").then((reg) => {
    reg.addEventListener("updatefound", () => {
      const w = reg.installing;
      w?.addEventListener("statechange", () => {
        if (w.state === "waiting")
          showUpdateToast(() => w.postMessage({ type: "SKIP_WAITING" }));
      });
    });
  });
  navigator.serviceWorker.addEventListener("controllerchange", () => location.reload());
}
```

## 8. Verification

- **(a) No `/api` response cached:** browse the app; DevTools → Application → Cache Storage → `cp-shell-*` must hold only `/`, `/index.html`, fonts, logo, `/assets/*`. In the console, `caches.match("/api/v1/dashboard")` and every `/api` match must resolve `undefined`. Repeat as a second user after logout — only their own live data appears.
- **(b) Shell loads offline:** after one online visit, enable DevTools offline mode, reload `/`, then load `/app/dashboard` directly: the shell renders with the §5 offline message.
- **(c) New deploy updates the shell:** change a visible string, rebuild (new `BUILD_ID`), reload: the toast appears; tap Refresh, the new string shows, Cache Storage holds one `cp-shell-*` cache, the old one gone. A full reload still lands the new shell.

## Requirements checklist

1. No authenticated response cached; nothing served across users/logout — §3, §6.
2. Shell loads offline after one online visit — §2, §5, 8(b).
3. New deploy reaches users; no stale shell forever — §1, §4, 8(c).
4. SSE and all `/api` bypass the worker completely — §3.
5. Hashed assets and a single `index.html` — §2, §3.
6. No background/periodic sync waking Render — no sync API is used.
7. All deliverables above — §1–§8.
8. Buildable as `public/sw.js` + manifest + `main.tsx` lines, no new dependency — §7.
