# CP Compass PWA — service-worker caching design

## The one rule

A user on a shared phone who opens the app offline must never see someone else's dashboard. So this design has one rule: **the worker only ever caches public, versioned, static files. It never caches, clones, or looks at an API response, and it never stores anything at runtime.**

## Open questions, resolved first

- **How does a hand-written `sw.js` know Vite's hashed names?** It can't — the build injects them ("Build step").
- **How does a deploy invalidate the old cache?** The cache name carries the deploy's git SHA. New deploy, new cache name; the old one is deleted on activation.
- **Shared device, or after logout?** Nothing private is in any cache, so there is nothing to purge and nothing to leak.

## Assumptions

- The manifest already exists with `start_url: "/"`, `scope: "/"`, and 192/512 px icons — no manifest change is needed. Vercel serves `/assets/*` with immutable caching (hashed names make this safe).
- The backend adds `Cache-Control: no-store` on every `/api/v1` response as defence in depth.

## Cache names and versioning

One cache only, no runtime cache:

```
cp-compass-shell-<BUILD_ID>   e.g. cp-compass-shell-a1b2c3d4
```

`BUILD_ID` is the 8-character Vercel git commit SHA, falling back to a build timestamp. There is deliberately no second cache: that is where private responses eventually land by accident. On activation, every cache starting with `cp-compass-` that is not the current name is deleted.

## Precache list (install time)

Precached, all same-origin and public: `/`, `/index.html`, `/compass.svg`, `/manifest.webmanifest`, every `/fonts/*.woff2` and every `/assets/*.js` and `/assets/*.css` from the build.

Deliberately **not** precached: anything under `/api/v1` — including public `/demo/*` data, because public is not the same as safe to freeze — any URL with a query string, and any cross-origin resource. `cache.addAll` is atomic: if any precached URL 404s, installation fails and the old worker keeps serving.

## Fetch-handler routing

| Request | Strategy | Why |
|---|---|---|
| `/api/v1/*` — every API call, `/demo/*`, and the SSE stream `GET /api/v1/sync/stream` | **Network-only, pass-through.** The handler returns without `respondWith` — never cloned, stored, or delayed. | The privacy guarantee: a response the worker never touches cannot leak to another user or survive logout, and pass-through cannot break SSE. |
| Navigations (`request.mode === 'navigate'`, any route incl. `/app/dashboard`) | **Network-first, cache fallback** to cached `/index.html`. | The shell is on Vercel, not the sleeping Render backend, so network-first is fast online and never serves a stale shell. Offline, the cached shell loads. |
| `/assets/*`, `/fonts/*`, `/compass.svg` | **Cache-first, no storing on miss.** Serve from the versioned cache; on a miss, fetch once and do not store it. | Hashed names are content-addressed: a cached file can never be the wrong version. |
| Everything else (same-origin `GET`) | **Network-only.** | No runtime caching, ever — this closes the hole where a future route gets cached by accident. |
| Non-`GET`, cross-origin, or any request with an `Authorization` header | **Pass-through, no `respondWith`.** | The worker must not see, store, or replay credentials. |

## The worker (`frontend/public/sw.js`)

`__BUILD_ID__` and `__PRECACHE__` are placeholders replaced at build time.

```js
const VERSION = '__BUILD_ID__';
const SHELL_CACHE = `cp-compass-shell-${VERSION}`;
const PRECACHE = __PRECACHE__; // ["/","/index.html","/compass.svg","/assets/index-a1b2.js", …]

self.addEventListener('install', (e) => {
  e.waitUntil(caches.open(SHELL_CACHE).then((c) => c.addAll(PRECACHE)).then(() => self.skipWaiting()));
});

self.addEventListener('activate', (e) => {
  e.waitUntil(caches.keys()
    .then((keys) => Promise.all(keys.filter((k) => k.startsWith('cp-compass-') && k !== SHELL_CACHE).map((k) => caches.delete(k))))
    .then(() => self.clients.claim())
    .then(() => self.clients.matchAll().then((cs) => cs.forEach((c) => c.postMessage({ type: 'SW_UPDATED' })))));
});

self.addEventListener('fetch', (e) => {
  const { request } = e;
  const url = new URL(request.url);
  if (request.method !== 'GET' || url.origin !== self.location.origin) return;
  if (url.pathname.startsWith('/api/v1')) return;
  if (request.mode === 'navigate') {
    e.respondWith(fetch(request).catch(() => caches.match('/index.html', { ignoreSearch: true })));
    return;
  }
  if (url.pathname.startsWith('/assets/') || url.pathname.startsWith('/fonts/') || url.pathname === '/compass.svg') {
    e.respondWith(caches.match(request).then((hit) => hit || fetch(request)));
    return;
  }
  e.respondWith(fetch(request));
});
```

## Build step (makes the placeholders real)

Add `scripts/inject-sw.mjs`, run last in `npm run build`. It globs `dist/assets/*.{js,css}` and `dist/fonts/*.woff2`, replaces `__BUILD_ID__` with `process.env.VERCEL_GIT_COMMIT_SHA?.slice(0, 8) ?? Date.now().toString(36)` and `__PRECACHE__` with the JSON list, and writes the result to `dist/sw.js`. No new dependency. If the script fails, the build fails — an unversioned worker never ships.

## Registration (`frontend/src/main.tsx`)

Production only, never dev:

```ts
if (import.meta.env.PROD && 'serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
  navigator.serviceWorker.addEventListener('message', (e) => {
    if (e.data?.type === 'SW_UPDATED') showUpdateToast(() => window.location.reload());
  });
}
```

`showUpdateToast` is a small "New version available — Reload" toast. No background or periodic sync exists here, so nothing ever wakes the sleeping Render backend.

## Update flow

1. A deploy ships a new `sw.js` and hashed assets; the browser installs it in the background on the next visit, leaving the current page untouched.
2. Install precaches the new shell, then `skipWaiting()` activates it, deleting every old `cp-compass-*` cache, claiming clients, and posting `SW_UPDATED`.
3. The user sees the toast and reloads when ready; the reload fetches `/index.html` network-first, so the new shell loads. No user is ever stuck on a stale shell: the old cache is deleted by name.
4. A user who never reloads keeps the old, working shell — safe, because it talks to the same versioned API.

## Offline behaviour

- **First visit must be online.** The worker installs and precaches on that visit; there is no offline first load.
- **Offline afterwards:** shell, fonts, and logo load from the versioned cache. A deep link such as `/app/dashboard` serves the cached `index.html`; the router renders the dashboard shell, its API calls fail, and the app shows its normal offline state with a retry — never stale data from a previous user, because no data was ever cached. The landing page is the same bundle, so it behaves identically. Render asleep is not offline: waking takes ~50 s, and the worker adds no timeout or retry.

## What is deliberately not cached, and failure recovery

Not cached: all `/api/v1` responses, the SSE stream, auth tokens, demo data, query-string URLs, cross-origin resources, and anything fetched at runtime. The cache holds only files identical for every user, so an entry can never be served to the wrong person.

If the worker itself is buggy, shipping a fixed `sw.js` with a new `BUILD_ID` replaces it on the next visit and deletes the bad cache on activation — no user action needed. As a kill-switch, deploy a `sw.js` whose `activate` handler unregisters the worker and deletes all `cp-compass-*` caches; the app then runs worker-free until a good worker ships.

## Verification (prove it before shipping)

1. **No API response is cached.** DevTools → Application → Cache Storage shows one `cp-compass-shell-*` cache with only the precached files — after using the app logged in, no `/api/v1` URL appears. Log out, log in as a different user, go offline: the dashboard shows the offline state, never the first user's data.
2. **Shell loads offline.** Load the app once online, then DevTools → Network → Offline, reload, and open `/app/dashboard` directly. Shell, fonts, and logo render; API panels show the offline state.
3. **A new deploy updates the shell.** Deploy a visible change and revisit: a new cache appears, the old one is deleted, the toast appears, and reloading shows the new version. Repeat with the previous tab still open to confirm the live session is never force-reloaded.
