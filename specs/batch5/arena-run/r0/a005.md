# CP Compass PWA: service-worker caching strategy

**Assumptions.** (1) The build can run one dependency-free Node script after `vite build`. (2) The app already shows an error/offline state when an API call fails — the worker reuses it. (3) Fonts are self-hosted woff2 under `/fonts/`.

## 0. First principles

Only two responses are safe to cache: public, immutable, same-origin static files (hashed names prove it), and the single unhashed shell entry point — only as a fallback. Everything else is per-user (every `/api/v1` response, including public `/demo/*`) or a live stream (SSE). So: cache the shell, never touch the API, and let the build — not a human — invalidate the cache.

## 1. Cache names and versioning

One cache only: `cp-shell-<BUILD_ID>`, e.g. `cp-shell-20261128-a1b2c3d`. `__BUILD_ID__` in `public/sw.js` is replaced at build by `scripts/sw-version.mjs` (no dependency) with the git short SHA plus timestamp; the script fails the build if the placeholder survives. A new deploy is a new cache; the old one is garbage, and there is no second cache to audit for leaks. `sw.js` bytes change on every build, which is what makes the browser detect the update (§6). No manual version bump — a forgotten bump is how users get stuck on a stale shell.

## 2. Precache list (install time)

Precached: `/` (index.html, as the offline fallback); every `/assets/*.js` and `/assets/*.css` discovered by parsing that fetched `/` for `src="/assets/…"` / `href="/assets/…"` — hashes are unknown at author time, so the worker discovers them; hardcoding them would break on the next build; `/compass.svg`. Fonts are not in the HTML, so the cache-first rule in §3 caches them on first use — offline after one visit. Install is best-effort (`Promise.allSettled`): a precache failure never fails it — runtime caching fills gaps on the first visit. NOT precached: anything under `/api/`, anything non-GET, anything cross-origin, anything with an `Authorization` header.

## 3. Fetch routing

| Request | Strategy | Why |
|---|---|---|
| `/api/*` (all `/api/v1/*`, `/demo/*`, `/health`, SSE `/api/v1/sync/stream`), any non-GET, any cross-origin | **No interception — return without `respondWith`** | The worker never sees the request, headers, or response, so it cannot store, replay, or delay it. Zero latency; a sleeping Render backend wakes only on a real user action. |
| Navigations (`mode: navigate`, `/`, `/app/*`, any deep link) | **Network-first, cache fallback** | `index.html` is unhashed and changes every deploy: online users must get the fresh copy; offline, the cached `/` boots the SPA, refreshed by each successful network response. |
| `/assets/*`, `/fonts/*`, `/compass.svg` (GET, same-origin) | **Cache-first, populate on miss** | Hashed filenames are content-addressed: bytes at that URL can never change, so a cached copy can never be stale. Only `200` same-origin responses are stored. |
| Everything else, same-origin GET | **Network-only, no caching** | Nothing else needs offline support; caching it only widens the audit surface. |

## 4. The worker — `frontend/public/sw.js`

```js
const CACHE = 'cp-shell-__BUILD_ID__'; // build-injected

self.addEventListener('install', (e) => {
  e.waitUntil((async () => {
    const cache = await caches.open(CACHE);
    const html = await fetch('/').then((r) => r.text());
    const urls = new Set(['/', '/compass.svg']);
    for (const m of html.matchAll(/(?:src|href)="(\/(?:assets|fonts)\/[^"]+)"/g)) urls.add(m[1]);
    await Promise.allSettled([...urls].map((u) => cache.add(u)));
    self.skipWaiting();
  })().catch(() => self.skipWaiting()));
});

self.addEventListener('activate', (e) => {
  e.waitUntil((async () => {
    for (const k of await caches.keys()) if (k.startsWith('cp-') && k !== CACHE) await caches.delete(k);
    await self.clients.claim();
  })());
});

self.addEventListener('fetch', (e) => {
  const u = new URL(e.request.url);
  if (u.origin !== location.origin || e.request.method !== 'GET') return;
  if (u.pathname.startsWith('/api/')) return; // API + SSE: complete bypass
  if (e.request.mode === 'navigate') {
    e.respondWith(fetch(e.request).then(async (r) => {
      if (r.ok) (await caches.open(CACHE)).put('/', r.clone());
      return r;
    }).catch(() => caches.match('/')));
    return;
  }
  if (u.pathname.startsWith('/assets/') || u.pathname.startsWith('/fonts/') || u.pathname === '/compass.svg') {
    e.respondWith(caches.match(e.request).then((hit) => hit || fetch(e.request).then(async (r) => {
      if (r.ok) (await caches.open(CACHE)).put(e.request, r.clone());
      return r;
    })));
  }
});
```

No Workbox, no background sync, no periodic sync, no push. At ~40 lines, the worker's cache behaviour is auditable by reading it.

## 5. Registration — `main.tsx` (and manifest)

```ts
if (import.meta.env.PROD && 'serviceWorker' in navigator)
  window.addEventListener('load', () =>
    navigator.serviceWorker.register('/sw.js').catch(() => {}));
```

Production only, never dev; `/sw.js` at the root gives scope `/`. Registration failure is swallowed — the app works without a worker, just without offline. No manifest change — it already exists (`CP Compass`, standalone) — but `start_url` must be `/` so an installed launch hits the cached shell.

## 6. Update flow

A deploy changes `sw.js` bytes (new `BUILD_ID`), so the browser detects a new worker on the next navigation and installs it. `skipWaiting()` + `clients.claim()` activate it at once — safe: the old page already holds its JS in memory, and the next navigation fetches fresh `index.html` network-first. On activation, every `cp-*` cache except the current one is deleted. The user sees nothing: no prompt, no banner, no forced reload. No stuck state: even if the update failed, online users still get fresh `index.html`.

## 7. Offline behaviour

After one online visit the shell is cached. Offline, any navigation — `/`, `/app/dashboard`, any deep link — serves the cached `/`, and React Router renders that route's shell (skeleton + existing offline notice). No data loads offline: API calls bypass the worker and fail at the network, so the app shows "you're offline" instead of data. Nothing private is ever shown offline, because nothing private was ever cached — after logout, or on a shared device: logout only clears the `cp_access_token` in localStorage; there is no per-user cache to purge. Login needs the network, so the login form renders offline but submitting fails normally.

## 8. Deliberately not cached — and if the worker is buggy

Not cached, ever: all `/api/v1/*` (dashboard, submissions, settings, sync, SSE), `/demo/*` and public-profile data (public, but fetched via `/api/v1` — caching them would blur the one rule protecting privacy), `Authorization` headers, non-GET requests, cross-origin responses. Recovery: (1) deploy a fixed `sw.js` — the byte change forces an update and `activate` wipes the old cache; (2) if the worker is broken beyond self-update, deploy a kill-switch `sw.js` that deletes all `cp-*` caches and unregisters itself; (3) locally, DevTools → Application → Service Workers → Unregister + Clear site data. Because `index.html` is network-first, online users are never locked out by a bad cache while a fix ships.

## 9. Verification

(a) **No API response is cached:** log in, use the dashboard, sync, then DevTools → Application → Cache Storage — only `cp-shell-<BUILD_ID>` exists, holding only `/`, `/assets/*`, `/fonts/*`, `/compass.svg`; in the console, `await caches.match('/api/v1/dashboard')` is `undefined`. Log out, log in as another user, confirm the dashboard shows only the second user's data. (b) **Shell loads offline:** after one online visit, DevTools → Network → Offline, reload `/` and go to `/app/dashboard` — the shell renders both times, assets from Cache Storage, API areas show the offline notice. (c) **New deploy updates:** change visible text, build, deploy, reload — the new worker activates, the old `cp-shell-*` cache is gone, the new hashed asset is served, the text change is visible.

## 10. Requirements checklist

1. No auth response cached, no cross-user/after-logout leak — §3 + §8. 2. Shell loads offline after one online visit — §2 + §3 + §7. 3. New deploy reaches users, no stale shell — §1 + §6. 4. SSE + every `/api` request bypass completely — §3, §4. 5. Hashed assets + single `index.html` — §2 + §3. 6. No background/periodic sync — §4; the worker never initiates a request.
