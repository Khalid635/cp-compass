# CP Compass PWA: service-worker caching strategy

## Principle

Cache only the public shell. Never touch private data: the worker never reads, stores, or replays an `Authorization` header, and never caches anything under `/api/`.

## Cache names and versioning

One cache only:

```js
const VERSION = "__BUILD_ID__"; // replaced at build time, see below
const SHELL = `cp-compass-shell-${VERSION}`;
```

`BUILD_ID` is the git short hash plus build time, injected by a build step (no new dependency):

```json
// package.json
"build": "vite build && node scripts/inject-sw-version.mjs"
```

`inject-sw-version.mjs` replaces `__BUILD_ID__` in `dist/sw.js` with e.g. `a1b2c3d-20261128T0439`. If the replacement ever fails, the build fails — a worker with a literal `__BUILD_ID__` must never ship, because every deploy would share one cache and updates would stop working.

A new deploy therefore gets a new cache name. The old cache is deleted on activation (below), so no stale shell can linger.

## Precache list

At `install`, precache only URLs whose names are stable across builds:

```js
const PRECACHE = ["/", "/index.html", "/compass.svg", "/manifest.webmanifest"];
```

Fonts are precached too, but only if their filenames are stable (e.g. `/fonts/inter-400.woff2`); if a font filename is hashed, do not list it — it is runtime-cached instead (below).

Deliberately **not** precached:

- Hashed JS/CSS under `/assets/*` — their names are unknown until Vite finishes, so listing them by hand is impossible and listing them wrong breaks install. They are cached on first use.
- `/sw.js` itself — it must never be cached (see "Failure mode").
- Anything under `/api/v1/*`, including `/demo/*` and `/health` — public demo data is still live data and must never be frozen in a cache.
- `localStorage` tokens — the worker never touches them.

If any entry fails, install fails and the old worker stays in control — a half-precached shell is worse than the old working one.

## Fetch-handler routing

Only same-origin `GET` requests are handled. Everything else — non-`GET`, cross-origin, requests with an `Authorization` header — returns immediately with no `respondWith`.

| Request | Strategy | Why |
|---|---|---|
| `/api/*` (all API, incl. `/demo/*`, `/health`, SSE `/api/v1/sync/stream`) | **Bypass completely: no `respondWith` at all** | No cache read, write, or latency is added; the SSE stream cannot be buffered or broken by the worker; no authenticated response can ever enter a cache. |
| Navigations (`request.mode === "navigate"`, e.g. `/`, `/app/dashboard`) | **Network-first, cache fallback** | Online users always get the newest `index.html` (new deploys reach them); offline users get the cached shell. On a network success, put the fresh `index.html` in `SHELL`. |
| `/assets/*` (hashed JS/CSS) | **Cache-first** | Filenames contain a content hash, so a file never changes in place; cache-first is safe and makes repeat loads instant. On a miss, fetch, cache only a `200` response, then return it. |
| `/fonts/*` (`.woff2`) | **Cache-first** | Same reasoning: versioned, immutable files. |
| `/compass.svg`, `/manifest.webmanifest`, other same-origin static files | **Stale-while-revalidate** | Instant from cache, refreshed in the background; and because they live in the versioned cache, a new deploy wipes them anyway. |
| Everything else same-origin `GET` | **Network-first, cache fallback** | Unknown future pages should not be frozen; the cache is only a fallback. |

Never `cache.put` unless: same origin, `GET`, status `200`, not under `/api/`, and no `Authorization` header.

## Update flow

```js
self.addEventListener("install", (e) => {
  e.waitUntil(caches.open(SHELL).then((c) => c.addAll(PRECACHE))
    .then(() => self.skipWaiting()));
});
self.addEventListener("activate", (e) => {
  e.waitUntil(caches.keys()
    .then((keys) => Promise.all(keys.filter((k) => k !== SHELL)
      .map((k) => caches.delete(k))))
    .then(() => self.clients.claim()));
});
```

1. New worker installs in the background and precaches the new shell.
2. `skipWaiting()` activates it immediately; `activate` deletes every cache whose name is not the current `SHELL`.
3. `clients.claim()` lets it control open tabs, but **no page is force-reloaded** — that could interrupt a sync or lose unsaved work.
4. `main.tsx` shows a small toast when an update is ready (see below). The user taps **Refresh** when ready; until then the old shell keeps running in memory.

## Registration (`main.tsx`)

```ts
if (import.meta.env.PROD && "serviceWorker" in navigator) {
  window.addEventListener("load", () => {
    navigator.serviceWorker.register("/sw.js").then((reg) => {
      reg.addEventListener("updatefound", () => {
        const worker = reg.installing;
        worker?.addEventListener("statechange", () => {
          if (worker.state === "installed" && navigator.serviceWorker.controller)
            showUpdateToast(() => window.location.reload());
        });
      });
    });
  });
}
```

Registration only in production builds, never in dev. The manifest needs no change beyond verifying: `name: "CP Compass"`, `display: "standalone"`, `start_url: "/"`, `scope: "/"`, and 192/512 px icons including a maskable one.

## Offline behaviour

After one online visit, offline the app loads: `index.html`, its JS/CSS, fonts, and logo — the whole shell. A deep link such as `/app/dashboard` works the same way: the navigation handler serves cached `index.html`, the SPA router mounts the dashboard route, and the page renders its shell. What does **not** load offline is data: every `/api/v1` call fails, so the UI must show its normal offline state (a "You're offline" banner and empty dashboard, not a blank page or endless spinner). No demo data is available offline, because `/demo/*` is never cached.

## What is deliberately not cached

`/api/v1/*` (dashboard, submissions, settings, sync, SSE, demo), any request with an `Authorization` header, any non-`GET` request, any non-`200` response, any cross-origin request, and `/sw.js` itself. There is no background sync and no periodic sync, so a sleeping Render backend is never woken by the worker.

## Failure mode: if the worker is buggy

Because `sw.js` is served with `Cache-Control: no-cache` (in `vercel.json`), a fix reaches users on their next visit. The kill-switch is a deploy of this minimal worker:

```js
self.addEventListener("install", () => self.skipWaiting());
self.addEventListener("activate", (e) => e.waitUntil(
  caches.keys().then((ks) => Promise.all(ks.map((k) => caches.delete(k))))
    .then(() => self.clients.claim())));
// No fetch handler: every request bypasses the worker.
```

It deletes all caches and then does nothing, so the app behaves as if no worker existed. A single user can also recover in DevTools: Application → Service Workers → Unregister, then Application → Clear site data.

## Verification

**(a) No API response is cached.** Use the app logged in, then in DevTools → Application → Cache Storage confirm the only cache is `cp-compass-shell-<BUILD_ID>` with no `/api/` entry. In the Network tab, `/api/v1` requests must be network requests, never "(from ServiceWorker)". Repeat after logout and login as a different user: no previous user's data appears.

**(b) Shell loads offline.** Load the app once online, then DevTools → Network → Offline, reload `/app/dashboard`: shell, logo, and fonts load and the offline banner appears. Also test a cold start: close the tab, go offline, open `/app/dashboard` fresh.

**(c) A new deploy updates the shell.** Change a visible string, rebuild, deploy, reload once: the update toast appears, Cache Storage shows the new `cp-compass-shell-<BUILD_ID>`, and the old cache is gone. Tap Refresh: the new string shows and the new hashed assets load.

## Assumptions

- `BUILD_ID` injection runs in the build (above); fonts have stable filenames or are runtime-cached.
- Vercel serves `/sw.js` with `Cache-Control: no-cache` and hashed `/assets/*` as immutable.
- The app already shows an offline banner/empty state when API calls fail; this design only guarantees the shell that renders it.
