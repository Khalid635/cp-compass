# Arena task — Batch 5, the one consequential design decision

## The decision

Design the service-worker caching strategy for the CP Compass PWA
(Progressive Web App) so the app is installable and its shell loads
offline, without ever leaking private data through a cache.

## Product context (what a stranger needs to know)

- CP Compass is a Codeforces training tracker. React 19 + Vite +
  TypeScript + Tailwind frontend (served from Vercel); FastAPI backend
  (Render, free tier, sleeps after ~15 min idle, ~50s cold start);
  Neon Postgres. JWT auth: a 15-minute access token in localStorage
  (`cp_access_token`), Authorization: Bearer header on every /api/v1
  call. All /api/v1 routes except /health and the read-only /demo/*
  routes require auth. The frontend is a single-page app: one
  index.html, hashed JS/CSS assets under /assets/.
- The app shell (what must load offline): index.html + JS/CSS bundles
  + fonts (self-hosted woff2 under /fonts) + the compass.svg logo.
- Live data (must NEVER be cached): everything under /api/v1 — the
  dashboard, submissions, settings, sync status. A sync-progress SSE
  stream runs at GET /api/v1/sync/stream while a sync is running.
- Public, cacheable data: the landing page is server-rendered HTML from
  the same SPA bundle (no separate static landing); /demo/* routes are
  read-only seeded demo data, public but still behind /api/v1.
- Constraints from the project: no new npm dependencies unless you
  justify one (the default is a hand-written service worker, no
  Workbox); the worker is registered only in production builds, never
  in dev; the backend runs on Render free tier, so the worker must not
  add request load (no background sync that hammers a sleeping backend).
- Users: one account per person, Codeforces handle attached. Some
  users share devices. The public-profile feature in this same batch
  is opt-in, default off.

## Hard constraints (non-negotiable — a design that breaks one loses)

1. NO authenticated API response is ever stored in any cache, and no
   cached response is ever served to a different user or after logout.
   The worker must not see, store, or replay Authorization headers.
2. The app shell (index.html + its JS/CSS/fonts) loads when the device
   is offline, after at least one online visit.
3. A new deploy must reach users reliably: no user stuck forever on a
   stale shell, no cache that never updates.
4. The SSE sync stream and every /api request bypass the worker
   completely (no fetch-handler interference, no extra latency).
5. The design must work with hashed Vite asset filenames (assets change
   names on every build) and a single index.html.
6. No background-sync or periodic-sync that wakes a sleeping Render
   backend.

## What the winning solution must contain (concrete, buildable)

- Exact cache names and versioning scheme (how a new deploy invalidates
  the old cache).
- The precache list: which URLs are precached at install time, and
  which are deliberately NOT precached.
- Fetch-handler routing rules: for navigations, for /assets/*, for
  /fonts/*, for /api/*, for everything else — each with its strategy
  (cache-first / network-first / stale-while-revalidate / network-only)
  and WHY.
- The update flow: how a new service worker activates, when old
  caches are deleted, and what the user sees (if anything).
- Offline behaviour: exactly what loads offline and what the user sees
  when they tap a deep link (e.g. /app/dashboard) while offline.
- What is deliberately NOT cached, and the failure mode if the worker
  itself is buggy (how to recover).
- Verification steps: how to prove (a) no /api response is cached,
  (b) the shell loads offline, (c) a new deploy updates the shell.

## What "done" looks like

A design a developer can implement directly as
frontend/public/sw.js + frontend/public/manifest.webmanifest + a few
lines in main.tsx — with no open questions left about caching,
updates, or privacy. Length: aim for a complete design in under 1200
words; a design that needs a second document to be buildable is
incomplete.

- Browsers are modern Chrome/Edge/Firefox/Safari.
- The Vite build emits hashed assets and a single index.html; the
  worker file lives at /sw.js (same origin, root scope).
