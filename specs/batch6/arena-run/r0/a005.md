# Arena a005 — Cookie-only auth behind a worker that never sees a token

**One line:** cookie-only auth, double-submit CSRF delivered in a JSON body (never `document.cookie`), and a service worker that returns before `respondWith` for anything authenticated — it may cache the shell, but can never store, replay, or poison a session.

## 1. The six decisions

**Q1. Cookie-only. No `Authorization` fallback.** One credential path. A fallback keeps a JS-readable token alive, re-opens the XSS theft this move closes, and defeats the worker gate (the old worker bypassed `Authorization` requests precisely because a header token is visible to it). `get_current_user` reads `request.cookies["cp_access"]` only; any `Authorization` header is ignored. No token lives in JS state that survives reload; the only in-memory secret is the CSRF token (Q4), which alone authenticates nothing.

**Q2. CSRF: double-submit + strict Origin/Referer. SameSite is not a layer.** Both checks on every state-changing request — `POST`/`PUT`/`PATCH`/`DELETE` to `/api/v1/*`, including login, register, verify-email, forgot/reset, totp-verify, refresh, logout, logout-all. Server compares `X-CSRF-Token` with the `cp_csrf` cookie via `hmac.compare_digest`; mismatch/missing is `403 {detail: "csrf_mismatch"}`, no state change. Independently, `Origin` must exactly match the allowlist (prod `https://cp-compass-phi.vercel.app`; dev `http://localhost:5173`, `http://localhost:4173`). If `Origin` is absent, `Referer` must match; if both are absent, reject. Browsers always send `Origin` on `fetch` POST and an attacker cannot spoof it (forbidden header), so a stolen CSRF token alone is useless from an attacker origin. SameSite counts for nothing in prod: prod cookies are `SameSite=None` (Q3), so they offer zero CSRF defence. Exempt, and why: safe methods `GET`/`HEAD`/`OPTIONS` (no endpoint mutates on GET — audit this); `GET /api/v1/auth/csrf` (issues only an unprivileged random token, idempotent per Q4); `GET /api/v1/sync/stream` (read-only SSE, Q5); Google callback `GET` (protected by HMAC-signed `state` + `code`, not CSRF). Nothing else is exempt; refresh is **not** exempt — it rotates credentials.

**Q3. SameSite: `None`+`Secure` in prod; `Lax`, not `Secure`, in dev — with a dev host fix.** Prod is genuinely cross-site (Vercel origin, Render cookie host), so `SameSite=None; Secure` is the only value under which the browser sends the cookie on cross-site `fetch`. Dev is plain HTTP and `Secure` cookies are silently dropped over HTTP, so dev is `Secure=False`. `SameSite=None` without `Secure` is rejected by Chrome/Firefox, so dev is `SameSite=Lax; Secure=False`. That works only if dev is same-site — ports do not affect same-site-ness, hosts do — so the frontend must call `http://localhost:8004`, **not** `http://127.0.0.1:8004` (different host = cross-site, and `Lax` withholds the cookie on cross-site POSTs: silent login loop). Required change: `VITE_API_BASE=http://localhost:8004`. One settings object (`COOKIE_SECURE`, `COOKIE_SAMESITE` from env) with a startup assert: `SameSite=None` requires `Secure`; prod never runs with `Secure=False`. No Vite `/api` proxy in dev, so dev exercises the real cross-origin path.

**Q4. CSRF lifecycle: `GET /auth/csrf`, in-memory only, rotated on auth-level change.** Token: `secrets.token_urlsafe(32)`, never stored in the DB. New `GET /api/v1/auth/csrf` returns `{"csrf_token": "<value>"}` in the JSON body **and** sets the `cp_csrf` cookie to the same value. The JSON body is load-bearing: JS on `cp-compass-phi.vercel.app` **cannot** read a cookie set for `cp-compass-api-1j9a.onrender.com` via `document.cookie` — a naive "read the cookie" design fails cross-site. So `cp_csrf` is `HttpOnly` too; JS keeps only the body copy in a module-level variable in `api/client.ts`, never in `localStorage`/`sessionStorage`, lost on reload. Issuance is idempotent: if a `cp_csrf` cookie is already present, return its value instead of rotating — otherwise any site could rotate the victim's token at will. Rotate only on login, TOTP verify, Google callback, password reset, and logout (logout clears it). Never on refresh or every GET — that would race concurrent tabs. `client.ts` calls `ensureCsrf()` on boot and before the first mutation (login/register/forgot/reset included); on `403 csrf_mismatch` it refetches once and retries once. `GET /auth/csrf` sends `Cache-Control: no-store`.

**Q5. SSE: cookie + `EventSource` with `withCredentials`. Kill `?token=`.** `new EventSource(url, { withCredentials: true })`. The access cookie is sent automatically; `decode_access_token_query` is deleted, so no token ever appears in a URL — no server log, history, or `Referer` leak. Works only because the cookie is `SameSite=None; Secure` in prod (Q3) and CORS stays an exact origin list with `allow_credentials=True`: an attacker origin gets no allow-origin echo, so its cross-site stream request is unreadable to attacker JS, and the stream exposes only the caller's own latest sync job and changes no state. `EventSource` cannot send `X-CSRF-Token`; acceptable, because the stream is a `GET` (exempt, Q2). `EventSource` gives no HTTP status, so on `onerror` `layout.tsx` closes the stream, calls `api.me()` (normal 401 → refresh → retry), and reopens once if `me()` succeeds; if `me()` 401s it stays closed and the app goes to login.

**Q6. Third-party cookies blocked: auth breaks completely — say so.** Prod cookies are cross-site, i.e. third-party. If blocked, login's `Set-Cookie` is silently dropped: login returns 200, the next `me()` is 401. No localStorage fallback — that violates constraint 1 and hands the token back to XSS. Instead, a login whose immediate `me()` 401s shows a full-page banner — "Signed in, but your browser blocked the session cookie (third-party cookies). Allow cookies for cp-compass-api-1j9a.onrender.com, then sign in again" — and no retry loop. Still works: public shell, landing page, offline shell (Section 4). Nothing authenticated works. Real fix (follow-up, not N4): serve the API from the same site (first-party subdomain, or a Vercel rewrite proxying `/api` to Render) so cookies become first-party.

## 2. Cookie table

One helper builds every cookie: `_cookie_kwargs(path, max_age)` → `httponly=True, secure=settings.COOKIE_SECURE, samesite=settings.COOKIE_SAMESITE`, plus `Cache-Control: no-store` on every response that sets one. `Domain` never set (host-only, Render host). Clearing re-issues with `Max-Age=0` and the **same** `Path`/`SameSite`/`Secure`, or the browser keeps the original.

| Cookie | Value / Max-Age | HttpOnly | Secure | SameSite | Path |
|---|---|---|---|---|---|
| `cp_access` | access JWT, 900 s | Yes | prod Y / dev N | prod `None` / dev `Lax` | `/api/v1` |
| `cp_refresh` | opaque refresh, 604800 s (7 d) | Yes | prod Y / dev N | prod `None` / dev `Lax` | `/api/v1/auth` |
| `cp_csrf` | `token_urlsafe(32)`, 604800 s | Yes (Q4) | prod Y / dev N | prod `None` / dev `Lax` | `/api/v1` |
| `cp_totp_pending` | TOTP-bridge JWT, 300 s | Yes | prod Y / dev N | prod `None` / dev `Lax` | `/api/v1/auth/totp-verify` |

Path scoping is least privilege: refresh only to `/api/v1/auth/*` (refresh, logout, logout-all), never to data/sync endpoints; TOTP cookie only to `totp-verify`. Login step 1 (TOTP required) returns `202 {totp_required: true, email}` and sets only `cp_totp_pending`; `totp-verify` reads it, sets `cp_access`/`cp_refresh`/`cp_csrf`, and clears it (`Max-Age=0`).

## 3. Backend changes

- `get_current_user`: reads `request.cookies["cp_access"]`, existing PyJWT HS256 verify; missing/expired/invalid → 401. No `Authorization` parsing.
- New helpers: `_set_auth_cookies(resp, access, refresh, csrf)`, `_clear_auth_cookies(resp)` (all four, each with its own path), `_issue_csrf()`, `_require_csrf(request)` dependency + Origin/Referer check on all mutating `/api/v1/*` routes; new `GET /api/v1/auth/csrf` (Q4).
- `login`: lockout unchanged; success sets three cookies, returns `AuthOut` with **no tokens** — `{email, cf_handle}` (+ `csrf_token` in body, same value as the cookie). TOTP-required sets only `cp_totp_pending`. `register` / `verify-email`: same on success; `verify-email` is a mutation, so it needs the CSRF header — frontend calls `ensureCsrf()` before submitting the code.
- `totp-verify`, Google callback: set cookies as above; the callback is a top-level `GET` navigation, so it sets cookies on the redirect back to the frontend (stored on redirect; frontend then calls `me()`).
- `refresh` (`POST /api/v1/auth/refresh`): reads `cp_refresh` cookie, rotates as today, reuse of a rotated token revokes the whole family; requires CSRF header; returns `{email, cf_handle}` only.
- `logout`: revokes one refresh token, clears all cookies. `logout-all`: revokes the family, clears all cookies.
- `/sync/stream`: auth from `cp_access` cookie; `?token=` and `decode_access_token_query` deleted; `Cache-Control: no-store`, `X-Accel-Buffering: no`.
- Forgot/reset: behaviour unchanged (JSON messages only, no tokens) but both are mutations needing the CSRF header; reset page calls `ensureCsrf()` on load.

## 4. Frontend changes, and the service worker

- `api/client.ts`: every `fetch` uses `credentials: "include"`; `Authorization` header and all token storage deleted. Module-level `let csrfToken: string | null` (in-memory only) + `ensureCsrf()` (`GET /auth/csrf`, credentials included); every mutation sends `X-CSRF-Token: csrfToken`. 401 flow unchanged in shape: single-flight refresh — one in-flight `POST /auth/refresh` shared by all waiters, retry once, on refresh 401 broadcast logout. Retry needs no token handling: the browser attaches the rotated cookie automatically. `BroadcastChannel("cp-auth")` (`{type: "logout"}` / `{type: "refreshed"}`) tells other tabs to drop their in-memory CSRF token and retry or redirect, so two tabs never present the same rotated refresh token. Network errors (`TypeError`, offline) are **not** 401s: no refresh, no logout, offline banner instead.
- `hooks/useAuth.tsx`: boot is `api.me()`; login/register/verifyEmail/verifyTotp/completeGoogleSignIn call `ensureCsrf()` first, then the endpoint, then `me()` — none stores anything. First boot after deploy deletes legacy `localStorage` keys `cp_access_token`, `cp_refresh_token` (and `sessionStorage` copies) before `me()`.
- `components/layout.tsx`: `EventSource` as in Q5, no `?token=`; `onerror` → close, `me()`-then-reopen-once.
- Types: `AuthOut` loses `access_token`, `refresh_token`, `token_type`; add `CsrfResponse {csrf_token: string}`, `LoginResponse {totp_required?: boolean, email: string, cf_handle?: string}`.

**The worker** (`frontend/public/sw.js`, Batch 5 winner a002) keeps its contract, now load-bearing: **only the public shell is ever cached**. Its fetch gates, in order, return without `respondWith` (plain browser fetch — cookies attached, `Set-Cookie` processed normally) for anything it must not touch:

```js
self.addEventListener('fetch', (event) => {
  const { request } = event;
  const url = new URL(request.url);
  if (request.method !== 'GET') return;                         // all mutations
  if (url.pathname.startsWith('/api/')) return;                 // every API call, incl. /auth/csrf
  if (request.headers.get('Accept')?.includes('text/event-stream')) return; // SSE
  if (request.headers.has('Authorization')) return;              // legacy tripwire; no longer sent
  if (url.origin !== self.location.origin) return;               // Render is cross-origin in prod
  if (url.searchParams.has('token')) return;                     // defence in depth; Q5 removes URL tokens
  // …only then: navigate → network-first, /assets/ → cache-first, /fonts|/compass.svg → cache-first
});
```

Gates are redundant on purpose: in prod the origin check alone bypasses `/api`, but in dev a same-origin Vite proxy would defeat it, so the `/api/` path gate must stay. The worker **cannot** read cookies — no `document` in a worker, `Cookie` header forbidden, `HttpOnly` invisible to JS — so it cannot leak, replay, or poison a session; it decides only on URL, method, and visible headers. Add one guard to cache helpers anyway: never `cache.put` a response with a `Set-Cookie` header, an opaque response, or a request with `credentials: "include"`. Cache keys are hashed same-origin asset URLs only — never a URL with a token or CSRF value. No auth work is delegated to the worker: no background-sync refresh, no periodic sync, no interception for retry. The 401 → refresh → retry flow runs entirely in the page, past the worker, because the worker never sees the request; no "worker in the middle" state exists, and a stale worker cannot serve a stale authenticated response because none was ever cached.

**Offline shell load:** the worker serves cached `/index.html` (network-first navigation falling back to `cp-shell-<BUILD_ID>`), which holds no user data and no tokens, so it is safe to serve to anyone. Cookies live in the cookie store, not Cache Storage, so they survive offline — but with no network `me()` throws a network error, not a 401, and `client.ts` must treat that as offline (banner + retry on `online`), never "logged out": no refresh, no cookie clearing, no login redirect. On logout the shell cache is deliberately **not** purged — it holds no auth data, and purging would break offline use; only cookies are cleared and the in-memory CSRF token dropped.

**Deploy / SW update:** a new `BUILD_ID` (injected by `scripts/inject-sw-build-id.mjs`) installs a new `cp-shell-<BUILD_ID>` cache; `skipWaiting()` + `clients.claim()` activate it, deleting only old `cp-shell-*` caches. Auth survives a worker update: cookies are origin-scoped to the backend, not the worker version; an old tab works on the old shell until reload. Kill-switch: a no-op `sw.js` whose `activate` deletes all caches and unregisters the worker (Batch 5 recovery).

## 5. Live session during the deploy

A live session is logged out once; accepted (one user). The backend stops reading `Authorization` at deploy, so an old tab's `localStorage` tokens are worthless; its next `me()` is 401, its refresh attempt is 401 (no refresh cookie exists), and the app redirects to login. The user signs in again and receives cookies. A refresh in flight at the deploy moment fails the same way. Legacy keys are deleted on first boot of the new frontend, so a returning browser never keeps a bearer token lying around.

## 6. Three most likely production failures, and the patch for each

1. **Silent login loop from cookie flags.** Wrong `SameSite`/`Secure` (e.g. `None` without `Secure`, or `Lax` against `127.0.0.1`) drops `Set-Cookie` with no error. Patch: startup assert (Q3); login-loop detector (login 200 then immediate `me()` 401 → Q6 banner, no retry); deploy check in a clean profile: login → reload → `me()` succeeds.
2. **Refresh reuse revokes the family after a lost response or second tab.** If the refresh response is lost (Render cold start / dropped connection), the client still holds the old cookie and a retry presents an already-rotated token — theft detection logs the user out everywhere. Patch: `client.ts` never auto-retries `refresh` (one attempt, single-flight per tab, `BroadcastChannel`); server-side, a 10-second grace window where the immediately-previous refresh token is accepted **only** if the token it rotated to has never been used — genuine theft reuse after that window still revokes the family.
3. **Stale shell or stale CSRF token after a deploy.** An old tab's in-memory CSRF token no longer matches a rotated cookie, or an old worker serves cached `/index.html` calling a changed endpoint shape. Patch: 403 `csrf_mismatch` → refetch `/auth/csrf` → retry once (Q4); versioned shell cache + `skipWaiting` so a byte-changed `sw.js` updates on next navigation; `Cache-Control: no-store` on `/auth/csrf` and all auth responses.
