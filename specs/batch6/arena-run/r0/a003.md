# Arena a003 — Cookie-only auth, Origin + double-submit CSRF, zero new state

## Verdict

Cookie-only auth, no `Authorization` fallback. CSRF is two cheap layers reusing things that already exist: an Origin/Referer exact-match check against the existing `CORS_ORIGINS` list, plus a double-submit cookie minted by the same helper that sets the auth cookies. No new dependency, no new DB table, no new env var, no server-side CSRF store. Diff: backend `auth.py` + `config.py` + `main.py`, frontend `client.ts` + `useAuth.tsx` + `layout.tsx`, one Vite proxy block for dev. The theft-detection core (`refresh_tokens`, rotation, reuse → revoke-family) is untouched — it never sees a token's transport, only its value. Anything not named below stays untouched.

## Q1 — Cookie-only, no Authorization-header fallback

`get_current_user` (`backend/app/auth.py:186`) reads the access JWT from the `cp_access` cookie instead of the `HTTPBearer` scheme; the `jwt.decode` + `type == "access"` block inside it is unchanged, only the token source line changes. The `bearer = HTTPBearer(auto_error=False)` line and its import are deleted. A fallback would keep two credential paths through every endpoint, keep a bearer token in JS (the exact theft path this batch exists to kill), and double the reasoning for every future endpoint. There is no API client to serve — the only client is our own frontend; manual testing uses a browser or `curl --cookie-jar`. Every endpoint using `Depends(get_current_user)` works with zero changes, because the choke point is one function.

## Q2 — CSRF: Origin check + double-submit, every mutation, no exemptions

One middleware in `main.py` (next to `_security_headers`, `main.py:142`), applied to `POST`/`PUT`/`PATCH`/`DELETE` only:

1. **Origin check (primary).** `Origin` must be an exact member of `CORS_ORIGINS` (`config.py:49`, already an exact list, never `"*"`, already containing the Vercel origin in prod). If `Origin` is absent, fall back to parsing `Referer` and checking its `scheme://netloc` against the same list. Neither present → fail closed, 403. Our frontend always sends `Origin` on a `fetch` POST; a form POST from an attack site sends a foreign one. Zero new config — it reuses a list that already has to be right for CORS.
2. **Double-submit (second layer).** The request must carry header `X-CSRF-Token` equal (via `hmac.compare_digest`) to the `cp_csrf` cookie. Missing header, missing cookie, or mismatch → 403 `{"detail": "CSRF token missing or mismatched"}`. Distinct detail strings per layer so a 403 is diagnosable from the response alone.

**Exemptions: none for unsafe methods.** Every mutation is checked — login, register, verify-email, resend-code, forgot/reset (N2, same batch), Google callback, totp-verify, refresh, logout, logout-all, 2FA setup/enable/disable, handle link/confirm, settings, notes, hints, reviews, delete-account. Middleware (not a per-endpoint dependency) is what makes this true: the N2 endpoints being built in the same batch are covered automatically, and a future mutation cannot forget the check. **GET/HEAD/OPTIONS are exempt**, safe because no GET mutates state — audit: `GET /auth/google` only builds the OAuth URL, `GET /sync/stream` is read-only, `GET /calendar/export.ics` is a read-only download, `GET /auth/me` is read-only. The one GET that writes anything is `GET /auth/csrf` (Q4), which only sets a random non-credential cookie.

**Bypass analysis.** *Stolen double-submit token:* an attacker site cannot read the `cp_csrf` cookie (different origin, no CORS read access), and knowing the value is useless — the victim's browser will not attach a custom `X-CSRF-Token` header to a cross-origin request from the attacker origin (custom headers force a CORS preflight, which fails for an unlisted origin). *Origin spoofing:* `Origin` is a forbidden header name — page JS cannot set it; only a non-browser client can spoof it, and one does not hold the victim's HttpOnly cookies. *Top-level GET / form POST:* cannot mutate (audit above); a form POST sends cookies but a foreign `Origin` and no `X-CSRF-Token` — blocked twice. Note: a Starlette `http` middleware cannot `raise HTTPException` into a response — it must `return JSONResponse({"detail": ...}, 403)`. OPTIONS passes through untouched so preflights never hit the check. **Rejected:** a server-side per-session CSRF store (new table/state on a 1-worker free tier, zero gain); per-request CSRF rotation (breaks parallel in-flight mutations from two tabs, buys nothing since the token's secrecy is not load-bearing).

## Q3 — SameSite: None+Secure in prod; Lax with NO Secure in dev, via a Vite proxy

| Cookie | Prod (Render HTTPS, cross-site) | Dev (plain HTTP localhost) |
|---|---|---|
| `cp_access` | `HttpOnly; Secure; SameSite=None; Path=/; Max-Age=900` | `HttpOnly; SameSite=Lax; Path=/; Max-Age=900` (no `Secure`) |
| `cp_refresh` | `HttpOnly; Secure; SameSite=None; Path=/; Max-Age=604800` | `HttpOnly; SameSite=Lax; Path=/; Max-Age=604800` (no `Secure`) |
| `cp_csrf` | `Secure; SameSite=None; Path=/; Max-Age=604800` (NOT HttpOnly — JS must read it) | `SameSite=Lax; Path=/; Max-Age=604800` (NOT HttpOnly, no `Secure`) |

No `Domain` attribute: host-only cookies for `cp-compass-api-1j9a.onrender.com` — `Domain=onrender.com` would share them with every other Render app. `Path=/`, not `/api/v1`: the Render origin serves only this API, so narrowing `Path` adds silent-failure risk for a future route and no safety.

Prod needs `SameSite=None` (frontend is cross-site to the API) and Chrome requires `Secure` with `None` — prod is HTTPS-only, so that is free. Dev cannot be `None` without `Secure`, `Secure` on plain HTTP means the cookie is never sent, and Chrome outright rejects a `SameSite=None` cookie without `Secure` — "None without Secure in dev" is not an option at all. The minimal fix is to make dev same-origin: one `server.proxy` (and `preview.proxy`) block in `vite.config.ts` mapping `/api` → `http://127.0.0.1:8004`, and leave `VITE_API_BASE` unset in dev so `client.ts` (`BASE = import.meta.env.VITE_API_BASE ?? ''`) issues relative requests through the proxy. Then the browser sees frontend and API as one origin, `SameSite=Lax` without `Secure` works on plain HTTP, and CORS is moot in dev. The `[::1]`-only `:4173` preview quirk is unaffected — the proxy is server-side Node connecting to `127.0.0.1:8004`. Flags come from config: `config.py` already computes `_looks_like_prod` (line 23, the same test `main.py:129` uses) — expose it as `IS_PROD`, plus `COOKIE_SECURE = IS_PROD` and `COOKIE_SAMESITE = "none" if IS_PROD else "lax"`, and delete the duplicate `_is_prod` in `main.py`. No new env vars.

## Q4 — CSRF token lifecycle: random value, minted twice, never rotated per request

- **Value:** `secrets.token_urlsafe(32)` from `new_csrf_token()` in `auth.py`. Not derived from the session or JWT — it only has to be unpredictable and equal on both sides.
- **Issued when:** (a) `GET /api/v1/auth/csrf` (new, ~4 lines: set the `cp_csrf` cookie, return `{"ok": true}`; GET, no auth, no DB, no rate limit — nothing to abuse); (b) re-issued with every login/refresh response by the same `_set_auth_cookies` helper that sets `cp_access`/`cp_refresh`. **Rotated when:** login and refresh only — never per request (Q2). **Stored where:** the `cp_csrf` cookie only (flags in Q3). No DB row, no server memory.
- **Before the first mutation:** `client.ts` gains `ensureCsrf()` — `if (!csrfToken()) await fetch(`${BASE}${V1}/auth/csrf`, {credentials: "include"})` — called once from the `useAuth` boot and lazily inside `request()` if the cookie is absent. `request()` reads it with a tiny `document.cookie` parser and sends `X-CSRF-Token` on unsafe methods. Login, register, forgot/reset and totp-verify are therefore covered before the user has any auth cookie. If `ensureCsrf` fails (offline), mutations fail closed with 403.
- **`totp_pending` does NOT become a cookie.** It stays a 5-minute JWT in the JSON body, held only in `useAuth` React state and sent back in the totp-verify body — exactly as today. Constraint 1 bans tokens in storage that persists across reloads; in-memory React state does not persist, and a reload mid-2FA just restarts login. Cookie-izing it would add a fourth cookie for zero gain.

## Q5 — SSE: cookie + `EventSource` with `withCredentials`, `?token=` deleted

`new EventSource(url, { withCredentials: true })` in `components/layout.tsx:89`, URL back to plain `` `${BASE}${V1}/sync/stream` `` — no token in the URL, so no JWT in server logs, browser history, or the `Referer` header. Backend: `sync_stream` (`main.py:780`) drops `token: Query(None)` and uses `Depends(get_current_user)` like every other authenticated GET; `decode_access_token_query` (`auth.py:158`) and `get_current_user_query` (`auth.py:174`) are deleted as dead code. The `_generate()` SSE generator is untouched. This works because CORS already has `allow_credentials=True` with an exact origin list — `withCredentials` is the one flag the browser needs to send cross-site cookies, and a plain `EventSource` GET needs no preflight. Edge cases: (1) the access cookie is 15 minutes and a long sync can outlive it — on `EventSource` error, `layout.tsx` does one silent refresh via the client and reopens the stream once; after that it closes the stream (`es.close()`, no infinite reconnect storm) and the existing poll fallback (`layout.tsx:87`, `sync/status` through `client.ts`) covers progress. (2) In dev the stream is same-origin through the Vite proxy, so `withCredentials` is a no-op. The service worker is untouched — it never caches `/api` and SSE already bypasses it.

## Q6 — Third-party cookies blocked: honest failure, detected, explained, no silent fallback

In prod the API cookies are third-party (`vercel.app` page, `onrender.com` cookie). If the user blocks third-party cookies, the browser will not set or send `cp_access`/`cp_refresh`/`cp_csrf` cross-site. What the user sees: the landing page loads, login returns 200, then the app immediately bounces back to the login screen — the session never sticks. What still works: everything unauthenticated — landing page, demo endpoints (`/demo/*`), public profile `/u/{handle}`, health. What breaks: all login, all authenticated pages, SSE. **There is no silent fallback that satisfies the hard constraints** — tokens back in `localStorage` would violate constraint 1, and no other browser storage holds cross-site credentials. So the fallback is detection + plain language: after any login/refresh returning 200, the next `api.me()` 401 means "cookies did not stick" (not "wrong password"), and the UI shows a banner: *"Your browser is blocking third-party cookies for cp-compass-api-1j9a.onrender.com, so the session can't be saved. Allow third-party cookies for this site (Chrome: Settings → Privacy → Third-party cookies → Add `[*.]onrender.com`), or use a browser profile that allows them."* The structural fix — serving the API same-site, e.g. a Vercel rewrite proxying `/api` → Render so cookies become first-party — is the documented future escape hatch, not this batch: it changes deployment topology, and streaming SSE through Vercel rewrites risks Hobby-plan timeouts cutting long streams.

## Backend changes (exact)

- `config.py`: expose `IS_PROD` (reuse `_looks_like_prod`), `COOKIE_SECURE`, `COOKIE_SAMESITE`. Nothing else.
- `auth.py`: add `_set_auth_cookies(response, tokens)` (sets `cp_access`/`cp_refresh` from the existing `issue_tokens` dict — `issue_tokens` itself is **unchanged**) and `_clear_auth_cookies(response)` (expiring all three cookies), plus `new_csrf_token()` set by the same helper. Change `get_current_user` to read `request.cookies.get("cp_access")`. Delete `decode_access_token_query`, `get_current_user_query`, the `HTTPBearer` scheme + import. **Unchanged:** `create_access_token`, `create_totp_pending_token`, `refresh_tokens` (atomic rotation + reuse → revoke-family), `revoke_refresh_token`, `revoke_all_refresh_tokens`, password hashing, lockout/ratelimit hooks.
- `main.py`: add the CSRF middleware (Q2) and `GET /api/v1/auth/csrf`. `AuthOut` (`main.py:245`) loses `access_token`, `refresh_token`, `token_type` → `{email, cf_handle}` only. Four return sites change from `return AuthOut(**tokens, email=..., cf_handle=...)` to "set cookies on the injected `Response`, return `AuthOut(email=..., cf_handle=...)`": verify-email (369), login (408), totp-verify (494/502), refresh (512). `login` (384): lockout, password check, TOTP branch unchanged; the TOTP branch still returns `{totp_required, pre_token}` with **no** cookies set. `google_callback` (421): HMAC state validation and user upsert unchanged; cookies instead of tokens. `refresh` (505): no body — read `cp_refresh` from the cookie, call `refresh_tokens(db, raw)` unchanged; on `None` (expired, or reuse → family revoked) return 401 **and clear all three cookies** so the client stops retrying. `logout` (516): no body — revoke the `cp_refresh` cookie's token if present, always clear cookies, always return `{"ok": true}` (idempotent). `logout-all` (523): logic unchanged, plus clear cookies. `me` (605): unchanged. `sync_stream` (780): Q5. `RefreshIn` (`main.py:195`) becomes unused by both its callers — delete it. `register` (319) and `resend-code` (372): no cookies, no response change — the email-code flow is untouched. All ~40 other `get_current_user` endpoints (dashboard, recommendations, revisions, analytics, calendar, postmortems, settings, export, notes, hints, ML): **zero changes**.

## Frontend changes (exact)

- `api/client.ts`: delete `accessToken()` (40), `refreshToken()` (44), `storeTokens()` (47). `clearTokens()` (53) becomes `clearLegacyTokens()` — still removes `cp_access_token`, `cp_refresh_token`, `cp_token`. Every `fetch` adds `credentials: "include"`. `tryRefresh()` (62): same single-flight `refreshPromise`, but `POST /auth/refresh` with **no body** and `credentials: "include"`; success is just `res.ok` (no tokens to store). `request()` (86) and `requestBlob()` (111): drop the `Authorization` header; on 401 and not retried, `tryRefresh()` once and retry; on failure, clear legacy keys and throw (same as today). Add the `csrfToken()` reader + `ensureCsrf()` (Q4) and the `X-CSRF-Token` header on unsafe methods. `streamUrl()` (~264): plain URL, no `?token=`. The `AuthResponse` type (133–157) loses the token fields; the `totp_required` / `pre_token` union is unchanged.
- `hooks/useAuth.tsx`: boot drops the `localStorage.getItem('cp_access_token')` gate (line 51) — boot always calls `api.me()`; 401 means logged out. Delete the four `storeTokens(...)` calls (77/90/97/112) — login/register/verifyEmail/verifyTotp/completeGoogleSignIn just call `api.me()` after success, as today minus storing. Boot also calls `ensureCsrf()` once. Logout calls `api.logout()` (no body), then clears legacy keys and sets user to null.
- `components/layout.tsx`: `new EventSource(url, { withCredentials: true })`; error path = one silent refresh + reopen, else close and use the existing poll fallback.
- `api/types.ts`, `pages/Auth.tsx`, the service worker, `main.tsx`: **untouched** (no token types live in `types.ts`; `Auth.tsx` never touches tokens directly; the worker never caches `/api`).
- Tests: the pytest suite uses `Authorization` headers — test-only change to cookie jars; no production logic changes for tests.

## Live-session migration + legacy keys

Deploy backend first, then frontend, minutes apart. A session live during the deploy dies with it: no server-side session store exists, the access JWT is 15 minutes, and the refresh rows in Neon survive but are unreachable — the new `refresh` reads the cookie only. The owner simply logs in again; no data is lost, and stale rows expire within 7 days (SHA-256 hashes, and presenting one is now impossible since no endpoint accepts a refresh token from a body). Side benefit: any refresh token previously exfiltrated from `localStorage` becomes unusable the moment the backend deploys. A user on the old JS bundle keeps sending `Authorization` headers → 401 → the old client's `clearTokens()` → login screen. Legacy keys in a returning browser are removed by `clearLegacyTokens()` at boot; they are already dead by then, so cleanup is hygiene, not security-critical.

## Three most likely production failures + patches

1. **Login 200, then immediate 401 on `/auth/me`** — cookies not set or not sent (prod `CORS_ORIGINS` missing the exact Vercel origin, or `Secure`/`SameSite=None` wrong). Diagnose in DevTools Network: `Set-Cookie` on the login response, `Cookie` header on `/auth/me`. Patch: fix `CORS_ORIGINS` in the Render env (config, not code); confirm `Secure; SameSite=None` and `Access-Control-Allow-Credentials: true`. Never "fix" this by dropping `Secure` in prod.
2. **All mutations 403 "CSRF origin not allowed"** — the frontend is served from an origin not in `CORS_ORIGINS`, e.g. a Vercel preview deployment (`cp-compass-*-git-*.vercel.app`) or the `:4173` preview origin. Patch: add that exact origin to `CORS_ORIGINS` (dev/preview env). Do not disable the check; the 403 detail names the received `Origin`, so the missing entry is obvious.
3. **SSE never opens / 401 loop during a long sync** — `withCredentials` forgotten, third-party cookies blocked, or the 15-minute access cookie expiring mid-sync. Patch: verify the stream request carries a `Cookie` header in DevTools; the `layout.tsx` error path (one refresh + reopen, then close + poll fallback) bounds the damage, and sync progress is never lost because `sync/status` polling is the fallback. If third-party cookies are the cause, it is Q6, not a code bug.

## What stays untouched (the point of this design)

`refresh_tokens` rotation/reuse logic, all revoke functions, password hashing, TOTP verify, login lockout + IP budget, Google OAuth HMAC state, the email-code flow, the N2 forgot/reset token logic (only its transport is now the shared middleware), all read endpoints, CORS config, security-headers middleware, body-size middleware, `models.py` (no new tables), the service worker, and every page except the three files named above. Known pre-existing wart, not fixed here: two tabs racing a 401 can both refresh with the same cookie — one wins, the other's token is already rotated, and reuse detection revokes the family (today's `localStorage` design has the identical race). For a one-user app the fix is a re-login; cross-tab refresh coordination (BroadcastChannel leader election) is the fancier option, rejected for Batch 6.
