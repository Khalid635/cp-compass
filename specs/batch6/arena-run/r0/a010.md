# Arena a010 — Zero-extra-round-trip cookies: piggybacked CSRF, single-flight refresh

Cookie-only auth, no header fallback. CSRF defence costs zero extra round trips because the token rides on responses the app already makes (boot `GET /me`, login), and refresh is single-flight with retry-once, so a flaky network can never spin a refresh loop or trigger rotation-reuse revocation. Every forced logout names its reason on screen.

## The six decisions

### 1. Cookie-only auth, no Authorization-header fallback

No fallback, ever. A fallback means any XSS can still exfiltrate a token from JS and the whole batch is theatre. `get_current_user` stops reading the `Authorization` header and reads the `cp_access` cookie only; a bearer token with no cookie gets a plain 401. Cost: SSE and OAuth need cookie-native solutions instead of a header crutch — that is the price, and it is the point.

### 2. CSRF: double-submit + Origin/Referer, on every mutation

Every POST/PUT/PATCH/DELETE under `/api/v1` — login, register, verify-email, forgot, reset, totp-verify, refresh, logout, logout-all, sync start/cancel, settings. Two layers: (a) **double-submit, enforced strictly** — header `X-CSRF-Token` must equal the `cp_csrf` cookie (`hmac.compare_digest`); missing/unequal → `403 {"code": "CSRF_FAILED"}`. An attacker's origin cannot read the cookie, so it cannot forge the header. (b) **Origin/Referer, enforced when present** — `Origin`, if present, must exactly match the CORS allow-list; else `Referer` must start with an allowed origin; mismatch → 403. If *both* are absent, double-submit alone decides, so privacy-hardened browsers that strip both headers keep working.

Exempt: GET/HEAD/OPTIONS (no state change), `GET /auth/google/callback` (cannot carry a header; protected by the existing HMAC-signed single-use `state`), and `GET /sync/stream` (read-only, own data only; EventSource cannot send custom headers, §5). Exempt GETs are safe because they mutate nothing and their responses are unreadable cross-origin under CORS.

### 3. SameSite: None+Secure in prod, Lax in dev behind the Vite proxy

**Prod:** `SameSite=None; Secure` on every cookie — `None` without `Secure` is rejected by browsers. **Dev:** `SameSite=Lax`, `Secure` off; a `Secure` cookie is never sent over plain HTTP, and the localhost secure-context quirk is real in Chrome but is **not** relied on. Lax cookies are not sent on cross-site fetch, so dev must not be cross-site: Vite dev (`:5173`) and preview (`:4173`) proxy `/api` to `127.0.0.1:8004`, so the browser sees same-origin localhost and cookies are first-party. Direct cross-origin fetch in dev bypassing the proxy will 401 — expected, not a bug. No `Domain` attribute anywhere (host-only cookies).

### 4. CSRF token lifecycle: piggybacked, never fetched

The backend sets `cp_csrf` on every `/api/v1/auth/*` response when absent — including the boot `GET /me` **401**, which is the pre-login supply — and rotates it on login, totp-verify, Google callback, logout and logout-all. **Never** rotated on refresh (parallel in-flight mutations would race the old value). Stored in the cookie only, `HttpOnly=false` (JS must read it), `Path=/`, `Max-Age=604800`, SameSite/Secure per §3. Value: `secrets.token_urlsafe(32)`; no server state, no DB lookup, zero latency cost. The frontend reads `document.cookie` fresh on every mutation (no cached copy) and sends `X-CSRF-Token`. There is **no** `/auth/csrf` endpoint — one would cost 1 RTT on every cold load and first mutation for zero security gain, since the token's secrecy comes from same-origin readability, not from a fetch. Pre-login mutations (login/register/forgot/reset) already have the token from boot `GET /me`, which runs on app mount before any human can submit a form. If the cookie is somehow absent, the request fails `403 CSRF_FAILED` and the UI shows a reload prompt; the form is never auto-resubmitted.

### 5. SSE: cookie + EventSource withCredentials, `?token=` deleted

`new EventSource(url, { withCredentials: true })`; CORS already allows credentials with an exact origin. The backend deletes `decode_access_token_query`: `/sync/stream` reads the `cp_access` cookie, and a `?token=` parameter, if present, is **ignored entirely** — never accepted, never logged. Native EventSource auto-reconnect is dangerous with an expired cookie (it would replay 401s forever), so `layout.tsx` owns reconnect: on error, close the source, run the single-flight refresh once, reopen **only** if refresh succeeded *and* a sync is still running; otherwise show a "Sync paused — sign in again" banner and stop. Backoff 1s → 2s → 5s cap, max 5 attempts per sync. The stream still bypasses the service worker, as today.

### 6. Third-party cookies blocked: honest degradation, no silent fallback

Prod is cross-site, so these are third-party cookies. Safari blocks them by default; Chrome/Firefox in strict modes too. **What the user sees:** login POST returns 200, the immediate `GET /me` returns 401 → the frontend detects "login succeeded but the session cookie did not stick" and shows a persistent banner ("Your browser blocked CP Compass sign-in cookies — allow cookies for cp-compass-api-1j9a.onrender.com, or use a browser that allows them") with per-browser steps. No login loop, no silent failure. **What still works:** the public landing page and static shell only; dashboard, sync, SSE and every authed call fail. **Fallback:** there is **no** localStorage / Authorization-header fallback — reintroducing one would silently restore the XSS theft this batch exists to remove. The real fix, if blocking becomes routine, is a future same-site deployment (custom domain or reverse proxy in front of Render); out of scope here, named so it is not invented mid-build.

## Round-trip budget

| Flow | Round trips |
|---|---|
| Cold login, fresh browser | Boot `GET /me` 401 + `Set-Cookie: cp_csrf` (1) → `OPTIONS` preflight for `POST /login` (1, cached afterwards) → `POST /login` (1, sets 3 cookies, returns user JSON) = **2 app RTTs**. Today it is 3 — the post-login `/me` is deleted because login returns `{email, cf_handle}` directly. TOTP adds exactly 1: `POST /totp/verify`. |
| Page reload, access valid | `GET /me` = **1 RTT**; app shell from the service-worker cache = 0. |
| Page reload, access expired | `GET /me` 401 (1) → `POST /refresh` (1) → retry `GET /me` (1) = **3 RTTs**. |
| 401 → refresh → retry, flaky mobile | Same 3 in the good case. On network error/timeout, refresh is retried **once** (max 2 attempts, 60s timeout each — a Render free cold start can take ~50s, so a 10s timeout would false-fail every cold start), then the original request is retried once, then stop. Worst case 5 RTTs, bounded, never infinite. |
| First mutation before any login | **0 extra** — the CSRF token arrived on boot. |

What security costs, stated plainly: the only security step that costs a round trip is refresh-on-401 (1 RTT + retry). It is worth it because the 15-minute access cookie keeps a stolen cookie useful for 15 minutes, not 7 days. Double-submit costs 0 RTT (piggybacked); the Origin check costs 0 RTT (the header is sent anyway). Preflights cost 1 RTT per (method, URL, headers) triple until cached — mitigate with `Access-Control-Max-Age: 86400` (browsers cap it, Chrome at ~2h, still zero preflights inside a session).

## Cookie table

| Cookie | Flags (prod / dev) | Path | Max-Age |
|---|---|---|---|
| `cp_access` | HttpOnly, Secure / no Secure, SameSite=None / Lax | `/` | 900 (15 min) |
| `cp_refresh` | HttpOnly, Secure / no Secure, SameSite=None / Lax | `/api/v1/auth` | 604800 (7 days) |
| `cp_csrf` | **not** HttpOnly, Secure / no Secure, SameSite=None / Lax | `/` | 604800 |
| `cp_totp` | HttpOnly, Secure / no Secure, SameSite=None / Lax | `/api/v1/auth` | 300 (5 min) |

The refresh cookie is path-scoped so it is only sent to auth endpoints, which is why there is no `__Host-` prefix (the prefix requires `Path=/`). `cp_totp` replaces the 5-minute `totp_pending` JWT: same value, now a cookie.

## Backend changes

- Settings `COOKIE_SECURE` / `COOKIE_SAMESITE` from env (prod `True`/`none`, dev `False`/`lax`); helpers `set_auth_cookies(resp, ...)` and `clear_auth_cookies(resp)` — clearing must repeat the identical flags **and** path with `Max-Age=0`, or the clear silently fails.
- `get_current_user`: read `request.cookies["cp_access"]` only; delete all `Authorization` parsing. New `require_csrf` dependency (§2) on every mutation. A small middleware ensures `cp_csrf` is set on every `/api/v1/auth/*` response when absent, including the 401 from boot `/me`, which an exception handler would otherwise strip the cookie from.
- `login`: CSRF-checked; success sets all three cookies, rotates CSRF, returns `{email, cf_handle}`. TOTP users: set only `cp_totp`, return `{totp_required: true}` — no token in JSON. Lockout unchanged.
- `register`, `verify-email`, `forgot`, `reset`: CSRF-checked, JSON messages only, otherwise unchanged.
- `totp-verify`: reads the `cp_totp` cookie, CSRF-checked; success sets auth cookies, clears `cp_totp`, rotates CSRF; missing/expired totp cookie → `401 TOTP_EXPIRED`.
- Google callback: CSRF-header exempt, `state` check unchanged; sets auth cookies + rotated CSRF, 302s to the frontend with only a success/error query param (no token in the URL); boot `GET /me` completes it (1 RTT).
- `refresh`: CSRF-checked, reads `cp_refresh`, rotation + reuse → revoke-family unchanged; returns `{email, cf_handle}`; in-memory rate limit (~10/min/IP).
- `logout` / `logout-all`: CSRF-checked, revoke via the `cp_refresh` cookie, clear all four cookies.
- `/sync/stream`: cookie auth, `?token=` ignored; a 401 ends the stream (frontend gates reconnect, §5).
- `AuthOut` becomes `{email, cf_handle}` only — `access_token`, `refresh_token`, `token_type` deleted. CORS gains `Access-Control-Max-Age: 86400`.

```python
def set_auth_cookies(resp, access, refresh, csrf):
    resp.set_cookie("cp_access", access, max_age=900, httponly=True,
                    secure=SECURE, samesite=SAMESITE, path="/")
    resp.set_cookie("cp_refresh", refresh, max_age=604800, httponly=True,
                    secure=SECURE, samesite=SAMESITE, path="/api/v1/auth")
    resp.set_cookie("cp_csrf", csrf, max_age=604800, httponly=False,
                    secure=SECURE, samesite=SAMESITE, path="/")
```

## Frontend changes

- `api/client.ts`: `credentials: "include"` on every fetch; delete token storage and the `Authorization` header; `csrfToken()` parses `document.cookie` per mutation and sets `X-CSRF-Token` on non-GET requests; single-flight refresh — one shared `refreshPromise`, waiters queue behind it; retry the original request once; on refresh 401/403 set state logged-out, redirect to `/login?reason=session-expired` with a toast, and never route the refresh call itself through the refresh path; timeouts 60s for refresh, 30s otherwise; error type gains `code` (`CSRF_FAILED`, `TOTP_EXPIRED`, `SESSION_EXPIRED`).
- `hooks/useAuth.tsx`: boot is still `api.me()` (which also supplies the CSRF cookie on its 401); login/register/etc. use the response user directly — no post-login `/me()`. On boot, one-time migration: delete `cp_access_token` and `cp_refresh_token` from localStorage. Login-success-but-`/me`-401 → the blocked-cookies banner (§6).
- `components/layout.tsx`: EventSource with `withCredentials`, gated reconnect (§5); `BroadcastChannel("cp-auth")` logout so all tabs leave together with a "Signed out in another tab" message, never a stale dashboard.
- Types: `AuthOut` without tokens; `ApiError { code?: string }`. The service worker needs no change (it never caches `/api`, SSE bypasses it) — verify in review.

## Failure UX — never silent, never looping

**Cookie blocked:** the §6 banner; the user stays on the login page. **CSRF 403:** inline "Security check failed — reload the page and try again" + Reload button; the mutation is **not** auto-replayed (non-idempotent) — reload re-boots and re-issues the token via `GET /me`. **Refresh fails:** toast "Your session expired — please sign in again", redirect to login with the original route kept in memory as `?next=`; no retry loop. **SSE dies:** "Live sync paused — sign in again" banner after backoff is exhausted.

## Live session during deploy + legacy keys

The deploy invalidates in-flight sessions by design: the backend no longer reads `Authorization` headers, and an old JS-held refresh token cannot be presented (there is no cookie). Recommend revoking all refresh families at deploy (one-time); the owner logs in once and sees "Sign-in upgraded to secure cookies — please sign in again". A returning browser's boot deletes `cp_access_token` / `cp_refresh_token` from localStorage (and any sessionStorage copy) once; no token value is ever read or sent after that.

## Three likeliest production failures + patches

1. **Third-party cookies blocked (Safari default).** Symptom: login 200 → `/me` 401, looking like a login loop. Patch: the §6 detection banner; test in the owner's daily browser before calling the batch done; long-term fix is the same-site proxy named in §6.
2. **Refresh race → family revoked.** Two tabs, or parallel 401s, refresh concurrently; the second presents an already-rotated token and reuse detection revokes the whole family. Patch: single-flight `refreshPromise` in the client (kills the in-tab race) **plus** a 10-second single-use grace window on the just-rotated refresh token — presenting it once more returns the same new pair instead of counting as theft; a second reuse, or any reuse after the window, still revokes the family. The grace slightly narrows theft detection; the alternative (random logouts on flaky mobile) is worse for a one-user app.
3. **CSRF desync after logout in another tab.** Tab B's in-flight mutation gets 401/403 with cleared cookies. Patch: `BroadcastChannel` logout sync, and on a lone `403 CSRF_FAILED` the client re-boots `GET /me` to re-issue the token and asks the user to retry manually — never an automatic replay loop.
