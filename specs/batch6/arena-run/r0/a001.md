# Arena a001 — HttpOnly cookies with Origin-gated CSRF: a stolen token dies with the tab

## Threat model

Assume the page is already hostile: a stored-XSS hole exists and an attacker's script runs in the user's origin. Under that assumption CSRF is moot — the attacker is already same-origin and can call any endpoint with the user's cookies. So this design does not pretend a CSRF token stops XSS. It optimises for one thing: **nothing the attacker can read may be reused after the session ends, and nothing from another origin may act at all.** HttpOnly cookies are the boundary: a script can *ride* the live session (unavoidable under XSS), but it can never *exfiltrate* a credential and come back tomorrow.

## The six decisions

### 1. Cookie-only auth. No Authorization-header fallback.

No fallback, no dual-read grace period, no `Authorization: Bearer` accepted anywhere after the cutover. A fallback is a second exfiltration channel: any code path that accepts a bearer token from JS is a path XSS can use to steal a long-lived credential. `get_current_user` reads exactly one thing: the `cp_access` cookie. The price is a hard cutover (see Migration), accepted deliberately — a transition window where both mechanisms work is a window where the old theft still works.

### 2. CSRF: Origin allowlist (load-bearing) + custom header (preflight gate) + double-submit cookie (belt-and-braces). All three, on every mutation.

Checked on **every** state-changing request — `POST/PUT/PATCH/DELETE` to any `/api/v1/*` endpoint, including `login`, `register`, `forgot-password`, `reset-password`, `verify-email`, `verify-totp`, `refresh`, `logout`, `logout-all`, `complete-google-signin`. No exemptions: login CSRF is real (an attacker logging the victim into the attacker's account to harvest their Codeforces sync data), so pre-login endpoints are checked too.

- **Origin/Referer (primary).** Reject any mutation whose `Origin` is absent-or-not-in-allowlist, falling back to `Referer` only when `Origin` is absent. The allowlist is the exact CORS origin list: `https://cp-compass-phi.vercel.app` in prod, `http://localhost:5173` and `http://localhost:4173` in dev. Browsers set `Origin` and forbid JS from overwriting it, so a cross-site attacker cannot forge it. **This is what makes CSRF impossible even with a leaked double-submit token**: the token is never sufficient on its own; a cross-site request fails the Origin gate before the token is even looked at.
- **Custom header `X-CSRF-Token` (preflight gate).** Every mutation must carry it. A cross-site form or `no-cors` fetch cannot set a custom header — the browser forces a CORS preflight, which the backend only answers for allowlisted origins with credentials. A plain cross-site form POST dies at preflight, token or no token.
- **Double-submit cookie (secondary).** The header value must equal the `cp_csrf` cookie value. This token is JS-readable by design, so under my threat model I assume it is stolen — and the design still holds, because Origin and the preflight gate do the real work. The double-submit check covers the case the other two miss: a same-site-but-cross-origin hole (e.g. a forgotten subdomain) where Origin passes but the attacker never saw the cookie value.

On failure: `403 {"detail": "csrf_check_failed"}` — the same message for all three failures, so a probe learns nothing about which gate tripped. Check Origin first, so a cross-site probe fails before any token comparison (and before any timing signal). The frontend treats a CSRF 403 as "refetch `/auth/csrf` once and retry once"; a second failure surfaces as a login prompt, never an infinite retry loop.

### 3. SameSite: `None; Secure` in prod, `Lax` + Vite proxy in dev.

Prod is genuinely cross-site (Vercel origin, Render origin), so `SameSite=None` is mandatory and `Secure` is mandatory with it. Dev is plain HTTP, so `Secure` cookies would simply never be set. I do **not** solve dev by shipping `SameSite=None` without `Secure` over HTTP (Chrome tolerates it on localhost; other browsers' behaviour has changed before). Dev instead makes the API same-origin: Vite `server.proxy` maps `/api` → `http://127.0.0.1:8004`, so the browser sees one origin (`localhost:5173`) and `SameSite=Lax`, `Secure=false` cookies work like first-party cookies. The Vite preview server (`:4173`, `[::1]`-only) gets the same proxy config. One `COOKIE_FLAGS` object switches on `ENVIRONMENT`: prod `{secure: True, samesite: "none"}`, dev `{secure: False, samesite: "lax"}`. If the proxy is ever removed, dev breaks loudly at login instead of silently degrading — that is a feature.

### 4. CSRF token lifecycle: anonymous token at boot, rotated on auth transitions, memory-only on the client.

- **Issued:** `GET /api/v1/auth/csrf` (new, unauthenticated) sets `cp_csrf` if absent and returns `{csrf_token}`. The frontend calls it on boot, before any mutation, and again after any CSRF 403. Pre-login mutations (login/register/forgot/reset) use this anonymous token — the Origin + preflight gates still apply, and the token is rotated on login so a pre-login token can never be replayed against an authenticated session.
- **Rotated on:** login, logout, logout-all, TOTP verification, Google sign-in completion, password reset, email verification. **Not on refresh** — rotating per refresh breaks parallel tabs (one tab refreshes, the other's in-flight mutation carries a stale token) and buys nothing, since the token is not the load-bearing defence.
- **Stored:** cookie `cp_csrf` (readable by JS — it has to be) plus an in-memory variable in `client.ts`. Never localStorage, never sessionStorage, never a persisted JS variable. A reload re-reads the cookie. Value: 32 random bytes via `secrets.token_urlsafe(32)`, stateless — validity is equality with the cookie, so no server state and no DB hit per mutation.

### 5. SSE: cookie + `EventSource(url, { withCredentials: true })`. The `?token=` parameter is deleted.

`GET /api/v1/sync/stream` authenticates through the same `get_current_user` cookie path as everything else — no query token, no `decode_access_token_query` (delete the function). `EventSource` sends cookies when `withCredentials: true` and CORS answers `Access-Control-Allow-Credentials: true` with the exact origin (already true today). Two things make this safe as a `GET`: the stream is read-only and exposes only the caller's own latest sync job (a cross-site navigation cannot read an EventSource response cross-origin), and I add the same Origin allowlist check to `/sync/stream` (EventSource always sends `Origin`). Server logs, browser history, and the `Referer` header never see a token again — that leak, not convenience, is why the query param dies rather than being kept as a fallback.

### 6. Third-party cookies blocked: login stops working, and there is no silent fallback.

Prod cookies are third-party cookies (set by `cp-compass-api-1j9a.onrender.com` while the user browses `cp-compass-phi.vercel.app`). If the browser blocks them, `Set-Cookie` on login is dropped and every subsequent call is an anonymous 401. **What the user sees:** the login form submits, appears to succeed, then the app immediately bounces back to the login screen. I detect this instead of letting it loop: after login, `useAuth` calls `api.me()`; if it 401s while the login response was 200, the UI shows a plain banner — "Sign-in didn't stick: your browser is blocking third-party cookies. Allow cookies for cp-compass-api-1j9a.onrender.com, or use a browser profile that allows them." Public pages still render; nothing authenticated works — no sync, no dashboard, no SSE. **There is deliberately no localStorage fallback**: a fallback that stores tokens in JS-readable storage to dodge a cookie block reintroduces exactly the XSS theft this design exists to kill. The real fix is structural and is recorded here as the follow-up, not smuggled into this batch: serve the API same-site via Vercel rewrites (`/api/*` → Render) so the cookies become first-party. That changes deployment, so it is a separate decision — but it is the only fix that is both secure and functional.

## Cookie table

| Cookie | Prod | Dev | Path | Max-Age |
|---|---|---|---|---|
| `cp_access` (access JWT, 15 min) | HttpOnly, Secure, SameSite=None | HttpOnly, Secure=false, SameSite=Lax | `/api/v1` | 900 |
| `cp_refresh` (opaque refresh, 7 d) | HttpOnly, Secure, SameSite=None | HttpOnly, Secure=false, SameSite=Lax | `/api/v1/auth` | 604800 |
| `cp_csrf` (double-submit, JS-readable) | Secure, SameSite=None, **not** HttpOnly | Secure=false, SameSite=Lax, not HttpOnly | `/` | 86400 |
| `cp_totp` (5-min TOTP-pending JWT) | HttpOnly, Secure, SameSite=None | HttpOnly, Secure=false, SameSite=Lax | `/api/v1/auth/totp-verify` | 300 |

Two deliberate details. `cp_refresh` is Path-scoped to `/api/v1/auth`, so the browser only ever sends the crown jewel to refresh/logout — never to `/sync/stream` or any future endpoint. I considered the `__Host-` prefix instead, but it forces `Path=/`, the opposite trade; path-scoping the refresh token wins. `cp_totp` is Path-scoped to the single endpoint that consumes it, so a script riding the session cannot even present it elsewhere.

## Backend changes

- `get_current_user`: reads `request.cookies["cp_access"]`, verifies the HS256 JWT exactly as today. No header path at all; missing/invalid → 401.
- `login`: unchanged lockout logic; on success sets `cp_access` + `cp_refresh` and rotates `cp_csrf`; on TOTP-required returns `202 {totp_required: true}` and sets only `cp_totp`. Returns `{email, cf_handle}` — **AuthOut loses `access_token`, `refresh_token`, `token_type` entirely.**
- `register`, `verify-email`, `forgot-password`, `reset-password`: set/rotate cookies the same way; recovery still returns JSON messages only, no tokens.
- `verify-totp`: reads `cp_totp` (not a JSON field), then sets `cp_access` + `cp_refresh`, rotates `cp_csrf`, clears `cp_totp`.
- Google callback: `complete-google-signin` sets cookies on the redirect response (SameSite=None; Secure is accepted on a cross-site redirect response) and redirects to the frontend with `?google=ok`; the frontend then calls `api.me()` — it must never trust the query param as proof of login. HMAC `state` check unchanged.
- `refresh`: reads the `cp_refresh` cookie; rotation and reuse → revoke-whole-family unchanged; sets new `cp_access` + `cp_refresh`; does **not** rotate `cp_csrf`.
- `logout`: revokes the one refresh token server-side, then clears all cookies with `Set-Cookie` using **exactly the same Path/SameSite/Secure as when set**, `Max-Age=0` — a clear with a mismatched Path silently fails and is the classic logout bug. `logout-all` revokes the family and clears the same way.
- `/sync/stream`: cookie auth + Origin check; delete `decode_access_token_query` and every `?token=` reference.
- New `GET /api/v1/auth/csrf`: sets `cp_csrf` if absent, returns `{csrf_token}`. New `require_csrf` dependency on all mutations: Origin/Referer allowlist → `X-CSRF-Token` present → equals `cp_csrf` cookie. A `set_cookie` helper centralises flags per environment — no endpoint hand-rolls flags.

```python
def set_auth_cookies(resp, access: str, refresh: str):
    resp.set_cookie("cp_access", access, httponly=True, max_age=900,
                    path="/api/v1", **COOKIE_FLAGS)
    resp.set_cookie("cp_refresh", refresh, httponly=True, max_age=604800,
                    path="/api/v1/auth", **COOKIE_FLAGS)
```

## Frontend changes

- `api/client.ts`: `credentials: "include"` on every fetch; delete all token storage, all `Authorization` headers, all `localStorage` reads. On boot, `GET /auth/csrf` and hold the token in module memory; every mutation sends `X-CSRF-Token`. The 401 → refresh → retry flow becomes: 401 → single-flight `POST /auth/refresh` (cookie rides along, CSRF-checked) → on success retry the original request once → on second 401, redirect to login. No token is ever held in a variable that survives reload.
- `hooks/useAuth.tsx`: boot is `ensureCsrf()` then `api.me()`; `login/register/verifyEmail/verifyTotp/completeGoogleSignIn` no longer store anything — they just call `api.me()` after success. On the login-succeeds-but-`me()`-401s case, show the third-party-cookie banner (Q6).
- `components/layout.tsx`: `new EventSource(url, { withCredentials: true })`; on stream error with a 401, refresh once then reconnect once.
- `types`: `AuthOut` drops the three token fields; add `CsrfResponse { csrf_token: string }`.

## Migration: live sessions and legacy keys

The deploy is a hard cutover. A session live during the deploy dies at the deploy: the next call after the new backend is up returns 401 (its localStorage token is ignored, its cookies don't exist yet) and the user re-logs in. That is acceptable for a one-user app and is stated here rather than papered over — the alternative, dual-read, keeps the XSS hole open through the transition. On first boot after the cutover, `client.ts` deletes the legacy keys `cp_access_token` and `cp_refresh_token` from both `localStorage` and `sessionStorage` (one-time cleanup, then never read again). The old access JWT remains cryptographically valid until its 15-minute expiry, but the backend no longer has any code path that accepts it, so it is inert — verify this by grepping the deployed backend for `Authorization` and confirming zero hits.

## Three most likely production failures, and the patch for each

1. **Login loop (third-party cookies blocked / ITP).** Symptom: login 200, `me()` 401, banner appears. Patch: short-term, the user adds a site exception; real patch, the Vercel `/api` rewrite so cookies become first-party (see Q6).
2. **CSRF 403s in a second tab after login in the first.** Symptom: tab B's mutations 403 after tab A logged in (CSRF rotated, tab B holds the old token in memory). Patch: the client's one-refetch-and-retry on CSRF 403 already heals this; if it recurs, confirm no code path rotates `cp_csrf` on refresh.
3. **Google OAuth callback sets no cookies.** Symptom: redirect lands, `me()` 401s. Cause: `Set-Cookie` on a cross-site 302 dropped, or a Path/SameSite mismatch. Patch: set cookies on the callback response *before* the redirect and verify in DevTools that `cp_access` arrives with `SameSite=None; Secure`; if the redirect still drops them, change the callback to return a same-origin landing page on the backend that sets the cookies and then navigates — never fall back to putting a token in the redirect URL.
