# Arena a009 — Two cookies, one Origin check, no CSRF token

## Principle

Every mechanism here is explainable in one sentence, and anything the new design makes dead gets deleted, not left as a fallback. Result: three cookies (two persistent, one five-minute), zero CSRF tokens, zero new endpoints, zero new dependencies, one CSRF check in one place. If a mechanism needs a paragraph to explain why it is safe, it is the wrong mechanism — so there is no double-submit token to steal, rotate, bootstrap, or leak, and no Authorization-header fallback keeping the old token path alive.

## The six decisions

### 1. Cookie-only auth. No Authorization-header fallback.

`get_current_user` reads `request.cookies["cp_access"]` and nothing else. A fallback is not defence in depth, it is a second attack surface: it keeps a JS-readable token path alive, doubles the code a reviewer must audit, and creates "which credential won?" confusion that breeds auth bugs. Every caller is our own frontend or our own EventSource, and both send cookies, so no legitimate caller needs the header. Delete the header parsing outright.

### 2. CSRF: Origin check only. No double-submit token, no SameSite reliance.

One middleware on every `POST`/`PUT`/`PATCH`/`DELETE` under `/api/v1`, zero exemptions: if the request `Origin` (falling back to the origin parsed from `Referer`) is not an exact match in `ALLOWED_ORIGINS`, return 403. `ALLOWED_ORIGINS` is the same constant as CORS `allow_origins` — exact match only, never substring or prefix.

Why this is safe: a browser always sends `Origin` on cross-site `fetch` POSTs and form POSTs, and page JavaScript cannot set or spoof it (`Origin` is a forbidden header name). An attacker page therefore arrives with the attacker's origin or with none, and both are rejected. `GET`s are exempt because none mutate anything — verify by grep, and convert any state-changing `GET` to `POST` rather than exempting a mutation. There is no token to steal (a stolen double-submit token is a full CSRF bypass), no token to leak in logs, and no bootstrap problem. `SameSite` is no defence here: prod needs `SameSite=None`, which by definition sends the cookie on cross-site requests, so any design leaning on `SameSite` in prod leans on nothing. `Referer` is only a fallback — our `Referrer-Policy: no-referrer` header means browsers usually omit it, so in practice this is `Origin`-only, and a missing `Origin` fails closed with 403. The risk is allowlist drift (failure mode 1); the check itself is fifteen lines with no per-route decoration to forget.

### 3. SameSite=None; Secure — identical in prod and dev.

Reject the tempting `Lax`-in-dev split: it is broken for this app. Dev is cross-site too (frontend `:5173`/`:4173` against backend `127.0.0.1:8004` are different sites), and `Lax` does not send cookies on cross-site `fetch` POSTs, so login would silently fail in dev while working in prod. One flag set everywhere: `SameSite=None; Secure`. It works on plain-HTTP loopback because browsers treat `localhost` and `127.0.0.1` as secure contexts and accept and send `Secure` cookies there; prod is HTTPS anyway. One code path, zero environment branches. Verify on Chrome and Firefox in the dev checklist before merging.

### 4. CSRF token lifecycle: there is none.

This is the payoff of decision 2. No `/auth/csrf` endpoint, no pre-login bootstrap call, no cookie the frontend must read before its first mutation, no chicken-and-egg for `login`/`register`/`forgot`/`reset` — those mutations are protected by the same `Origin` check as every other mutation and need no prior state. A design needing a token before login must invent an unauthenticated token-issuing endpoint, a rotation rule, and a story for stale tokens; this design has none of those because there is no token.

### 5. SSE: cookie + EventSource withCredentials. Delete `?token=`.

`layout.tsx` opens `new EventSource("/api/v1/sync/stream", { withCredentials: true })` and `/sync/stream` authenticates through the same `get_current_user` as every other endpoint. `EventSource` sends cookies automatically with credentials on, and CORS already allows credentials with an exact origin. Delete `decode_access_token_query` and the `?token=` parameter: a URL token lands in Render access logs, browser history, and the `Referer` header — the one place the old design leaked a live credential into places nobody audits.

### 6. Third-party cookies blocked: honest failure, no fallback that reintroduces the vulnerability.

In prod the backend is a third-party origin to the Vercel frontend, so blocking third-party cookies breaks auth visibly: login returns 200 but the `Set-Cookie` is dropped, so the immediate `api.me()` after login returns 401. The frontend detects exactly that sequence (login 200, then `me()` 401) and shows a banner: "Sign-in needs third-party cookies allowed for cp-compass-api-1j9a.onrender.com — allow them in your browser settings, then try again", with a retry button. Public pages still render; nothing authenticated works. That is the whole fallback, deliberately: there is no localStorage fallback, ever, because storing tokens in JS-readable storage on cookie failure reintroduces the exact XSS token-theft this batch exists to remove. The real long-term fix is serving the API from a same-site subdomain (e.g. `api.` on the app's own domain) so cookies become first-party; that is DNS work, out of this batch.

## Cookies

One helper owns every flag; nothing sets a cookie anywhere else: `resp.set_cookie(name, value, max_age=max_age, httponly=True, secure=True, samesite="none", path="/")`.

| Cookie | Max-Age | Set / cleared |
|---|---|---|
| `cp_access` | 900 (15 min) | Login, refresh, TOTP verify, Google callback. Cleared on logout. |
| `cp_refresh` | 604800 (7 days) | Same as access; rotated on every refresh. |
| `cp_totp` | 300 (5 min) | Login step 1 only, when TOTP is enabled. Cleared on verify. |

`Domain` is unset (host-only). `Path=/` for all three: a `Path=/api/v1/auth` restriction on the refresh cookie was considered and rejected — it adds a second rule and a real failure mode (logout would not receive the cookie) for no gain, since `HttpOnly` already blocks JS theft and the `Origin` check already blocks CSRF. Three cookies is the total; a double-submit design needs four.

## Backend changes

- `get_current_user`: read `cp_access` from `request.cookies`, verify with the existing HS256 code, 401 if missing or invalid. No header parsing remains.
- `login`: lockout and TOTP branching unchanged; on success set access + refresh cookies and return `{email, cf_handle}`; if TOTP is enabled, set only `cp_totp` and return `{totp_required: true, email}`. No tokens in JSON.
- `totp-verify`: read `cp_totp`, verify the code, then set access + refresh cookies and clear `cp_totp`. `verify-email`: no tokens involved; returns its message only, covered by the `Origin` middleware.
- Google callback: same as login — set cookies server-side, redirect with no tokens in the URL (e.g. `?google=ok`); the frontend then calls `api.me()`. Never put a token in a redirect URL.
- `refresh` (`POST` only): read `cp_refresh`, run the existing rotation logic unchanged, set the new pair, return `{email, cf_handle}`. Reuse of an already-rotated refresh token still revokes the whole family.
- `logout` / `logout-all` (`POST` only): revoke server-side exactly as today, then clear all three cookies with `Max-Age=0` and the same flags (a clear with different flags silently fails to clear).
- `/sync/stream`: cookie auth via `get_current_user`; `decode_access_token_query` deleted. `AuthOut` becomes `{email, cf_handle}` plus `totp_required` only on the login response; `access_token`, `refresh_token`, `token_type` are deleted, not deprecated.

## Frontend changes

- `api/client.ts`: every request uses `credentials: "include"` in the one fetch wrapper — that single line is the whole cookie story. Delete the `Authorization` header injection and all token storage. The 401 flow keeps its shape: on 401, single-flight `POST /auth/refresh` (cookies included), retry once; on a second 401 clear user state and go to the login page. After a 200 login, call `api.me()`; a 401 there means cookies were blocked and triggers the banner from decision 6.
- `hooks/useAuth.tsx`: boot is `api.me()` as today; `login`/`register`/`verifyEmail`/`verifyTotp`/`completeGoogleSignIn` no longer store anything — they set user state from the response and call `api.me()`.
- `components/layout.tsx`: `EventSource` with `{ withCredentials: true }`, no token in the URL. `types`: remove the token fields from `AuthOut`. Delete the `cp_access_token`/`cp_refresh_token` localStorage keys on boot (two lines, kept permanently).

## Live session during deploy, and legacy keys

A session live during the deploy breaks once, cleanly: the backend stops reading `Authorization` headers at deploy time, so the next request returns 401 and the user logs in again. That is tolerable for a one-user base — say it in the deploy note, do not pretend otherwise. As a one-time deploy step, revoke all refresh-token families server-side so no pre-deploy refresh token remains redeemable. Legacy `localStorage` keys are deleted by the frontend on boot (above); after that they are inert even if the cleanup line is ever removed, because no endpoint accepts a token from a body or header any more.

## Three ways this fails in production, and the patch for each

1. **Allowlist drift.** A new Vercel preview origin not in `ALLOWED_ORIGINS` makes every mutation 403; worse, if someone "fixes" it with a substring match, `evil-cp-compass-phi.vercel.app` passes. Patch: `ALLOWED_ORIGINS` is the single constant shared with CORS (exact match, no substrings, no regex), the deploy checklist tests the matrix (correct origin passes, evil origin 403s, missing origin 403s), and a spike in mutation 403s pages the owner.
2. **Third-party cookies blocked, or `Secure` on loopback rejected in some browser.** Symptom is the login-200-then-`me()`-401 sequence, which the banner already names and explains; the patch is the allow-instructions in the banner plus the same-site-subdomain move from decision 6. Never patch it with a localStorage fallback.
3. **Credentials dropped on one call path.** A `fetch` without `credentials: "include"` or an `EventSource` without `withCredentials` silently 401s on exactly one feature (SSE is the usual victim). Patch: `credentials` lives in the one wrapper, not at call sites, and the pre-merge grep is `new EventSource` and bare `fetch(` — exactly one of the former, zero of the latter outside the wrapper.

## What gets deleted

`decode_access_token_query`; `?token=` on the SSE URL; `Authorization` header parsing in `get_current_user`; `access_token`/`refresh_token`/`token_type` from `AuthOut` and every response; all `localStorage` token reads and writes; the never-built `/auth/csrf` endpoint; and the entire CSRF-token lifecycle (issue, rotate, store, bootstrap). Net effect: fewer cookies than a double-submit design, fewer endpoints than today, and one CSRF rule a reviewer can verify by reading fifteen lines.
