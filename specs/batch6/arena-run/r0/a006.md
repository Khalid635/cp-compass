# Arena a006 — Cookie-only auth, Origin + double-submit CSRF, every choice cited to a spec

## Authorities

RFC 6265bis, the OWASP CSRF Prevention and Session Management cheat sheets, and the Fetch/CORS spec decide this design; where a popular option breaks one, it is rejected with the rule cited. Three rules do most of the work. (1) RFC 6265bis: `SameSite=None` **must** carry `Secure`, and a `Secure` cookie is sent only over a secure channel, so it can never work on plain-HTTP localhost. (2) Fetch: a cross-origin `fetch` sends cookies only with `credentials: "include"`, and the server must then answer with an exact `Access-Control-Allow-Origin` (never `*`) **and** `Access-Control-Allow-Credentials: true` — one without the other fails. (3) OWASP ranks CSRF defences: Origin/Referer validation first, then a synchronizer/double-submit token; SameSite alone is explicitly not sufficient, and it offers nothing at all when the cookie is `SameSite=None`.

## Q1 — Cookie-only auth, no Authorization-header fallback

Cookie-only. `get_current_user` reads the access JWT from the `cp_at` cookie and nothing else; the `Authorization` path is deleted. A fallback would defeat the migration: any XSS that can read a header token can read it exactly as it reads localStorage today, and two auth paths diverge in precedence, logging and revocation. The only client is the React app, and SSE (Q5) also works with cookies, so no legitimate client needs a header. `decode_access_token_query` is deleted, not deprecated.

## Cookie names and flags (prod AND dev)

No `Domain` on any cookie (it widens it to subdomains for no benefit). `HttpOnly` on every token cookie.

| Cookie | Prod (Vercel -> Render, cross-site, HTTPS) | Dev (Vite :5173 -> 127.0.0.1:8004, HTTP) |
|---|---|---|
| `cp_at` — access JWT | `HttpOnly; Secure; SameSite=None; Path=/api/v1; Max-Age=900` | `HttpOnly; SameSite=Lax; Path=/api/v1; Max-Age=900` |
| `cp_rt` — opaque refresh | `HttpOnly; Secure; SameSite=None; Path=/api/v1/auth/refresh; Max-Age=604800` | `HttpOnly; SameSite=Lax; Path=/api/v1/auth/refresh; Max-Age=604800` |
| `cp_csrf` — double-submit | `Secure; SameSite=None; Path=/; Max-Age=86400`, **not** `HttpOnly` (JS must read it) | `SameSite=Lax; Path=/; Max-Age=86400` |
| `cp_tp` — TOTP-pending | `HttpOnly; Secure; SameSite=None; Path=/api/v1/auth/totp-verify; Max-Age=300` | `HttpOnly; SameSite=Lax; Path=/api/v1/auth/totp-verify; Max-Age=300` |

`Path=/api/v1/auth/refresh` on `cp_rt` means the refresh token is sent only to the one endpoint that needs it (OWASP least exposure). No `__Host-` prefix: it requires `Secure` *and* `Path=/` *and* no `Domain` (RFC 6265bis §4.1.3) — satisfiable in prod, impossible on HTTP dev; a name that changes between environments is a bug factory. One `COOKIE_SECURE` / `COOKIE_SAMESITE` setting flips the flags; names never change.

## Q3 — SameSite: None+Secure in prod, Lax in dev, via a dev proxy

**Prod: `SameSite=None; Secure`.** Frontend and backend are different sites, and a cross-site `fetch` is not a top-level navigation — `Lax` cookies are *not* sent on cross-site subresource requests, so `Lax` in prod means every API call arrives unauthenticated. That RFC 6265bis rule forces `None`, and `None` forces `Secure`.

**Dev: `SameSite=Lax`, no `Secure`** (a `Secure` cookie is never sent over `http://127.0.0.1:8004`). But `Lax` alone does not fix dev: Vite on `localhost:5173` fetching `127.0.0.1:8004` is cross-site, so a `Lax` cookie would not be sent on `POST /auth/login` either. The spec-compliant fix is to make dev same-site, not weaken the cookie: add a Vite proxy, `server.proxy: { "/api": { target: "http://127.0.0.1:8004", changeOrigin: true } }`, and call relative `/api/v1/...` in dev. The browser then sees one origin, the cookie is first-party, and `Lax` is ample. Do **not** "fix" dev with `SameSite=None` without `Secure`: Chrome rejects it outright and Firefox treats it as `Lax` — silent, environment-dependent breakage.

## Q2 — CSRF: Origin check AND double-submit token

Prod cookies are `SameSite=None`, so SameSite provides **zero** CSRF protection in prod — a cross-site `POST` from `evil.example` carries the cookies. Two independent checks, both required on every state-changing request:

1. **Origin check (primary, OWASP's first-ranked defence).** Reject any `POST/PUT/PATCH/DELETE` whose `Origin` is not exactly `https://cp-compass-phi.vercel.app` in prod (`http://localhost:5173`, `http://[::1]:4173` in dev). Fetch *always* sends `Origin` on a CORS `POST` and on any `POST` with a non-simple content type — every JSON mutation here qualifies. A missing `Origin` on a mutation is also rejected: this app has no legitimate same-origin form POST. Origin cannot be spoofed by a web attacker: the browser sets it, JS cannot overwrite it (a forbidden header name in Fetch).
2. **Double-submit token.** `cp_csrf` must be echoed as `X-CSRF-Token` and equal the cookie value, compared with `hmac.compare_digest`. This covers the Origin check's one hole — a same-site cross-origin subdomain attack — and any future client that omits `Origin`. A stolen token alone does **not** break this: the attacker still needs the victim's browser to send the `HttpOnly` cookies *and* pass the Origin check, and a cross-site page cannot read `cp_csrf` (a `fetch` from `evil.example` fails CORS before any response is readable) nor set the header on a simple form POST.

**Checked:** every `POST/PUT/PATCH/DELETE` under `/api/v1` — login, register, verify-email, forgot/reset password, totp-verify, refresh, logout, logout-all. **Exempt:** `GET`/`HEAD` only, and only because none mutates state — verify, don't assume: `/sync/stream` opens a stream, `/auth/csrf` mints a token, `/auth/me` reads. A `GET` that changed state would be a CSRF hole by itself, since a top-level `<img src>` navigation sends `Lax` cookies and needs no Origin. **Referer is never a check:** the app already sends `Referrer-Policy: no-referrer`, and browsers suppress `Referer` on HTTPS→HTTP and under strict policies, so it would false-reject legitimate requests. **On failure:** `403 {"detail": "csrf_check_failed"}`, no distinction between bad Origin and bad token in the response (the reason goes to server logs only — never hand an attacker an oracle). The frontend re-fetches a CSRF token once and retries once; a second failure surfaces as an error, never a silent loop.

## Q4 — CSRF token lifecycle

- **Issued:** `GET /api/v1/auth/csrf` (new, public, no auth) sets `cp_csrf` and returns `{"csrf_token": "<same value>"}`; the frontend reads it from the *response body*, not `document.cookie`. The same `Set-Cookie` is attached to `GET /api/v1/auth/me`.
- **Pre-login:** login, register, forgot/reset password are mutations and are checked like any other — the frontend calls `GET /auth/csrf` on app boot and on the auth pages' mount before the user can submit. The token is a random 32-byte value (`secrets.token_urlsafe(32)`), stored only as the double-submit pair. It is **not** bound to a session pre-login (there is no session yet); binding is impossible and unnecessary — the Origin check carries the pre-login defence, the token adds depth.
- **Rotated:** on login, successful TOTP verification, Google OAuth completion, and logout — every authentication-state change (OWASP: rotate on privilege change). **Not** per request and **not** on refresh: per-request rotation breaks parallel tabs and in-flight retries, and rotation on refresh would invalidate the token mid-flight for the SSE reconnect.
- **Stored:** the `cp_csrf` cookie plus an in-memory copy in `client.ts` (a module variable, lost on reload — boot re-fetches it). Never localStorage, never a persisted JS variable.

## Q5 — SSE: cookie + `withCredentials`. `?token=` deleted

`layout.tsx` opens `new EventSource("/api/v1/sync/stream", { withCredentials: true })` (relative URL through the Vite proxy in dev; absolute Render URL in prod). `withCredentials: true` is what permits cookies on a cross-origin request, and the server must answer with the exact origin plus `Access-Control-Allow-Credentials: true`. `EventSource` sends `Origin`, so the backend applies the same Origin allow-list to the stream. The JWT comes from the `cp_at` cookie; `decode_access_token_query` and `?token=` are removed. A URL token lands in Render access logs, browser history, and the `Referer` header — and `EventSource` cannot set an `Authorization` header, which is precisely why cookies (sent automatically, never in the URL) are the correct mechanism. The stream stays read-only and user-scoped (only the caller's latest sync job), so a cross-site `<img>`-style inclusion cannot exfiltrate it: the response is an event stream, not readable cross-origin, and the Origin allow-list rejects non-app origins. On a stream `401`, the frontend closes the `EventSource`, runs the refresh flow, and re-opens it — never by appending a token.

## Backend changes

- `get_current_user`: read `cp_at` from `request.cookies` only.
- `login` / `register` / `verify-email` / `forgot-password` / `reset-password`: return `AuthOut` without tokens (below); set `cp_at`, `cp_rt`, `cp_csrf` (freshly rotated); require Origin + double-submit.
- `totp-verify`: reads pending state from the `cp_tp` cookie, never from a JSON body the frontend stores; on success clears `cp_tp` and sets `cp_at`/`cp_rt`/`cp_csrf` (rotated). The 5-minute expiry is enforced from the JWT `exp` inside it, not from the cookie alone.
- Google OAuth callback: on the top-level `GET` redirect from Google, validate the HMAC `state`, then set `cp_at`/`cp_rt`/`cp_csrf` on the `302` redirect to the frontend (`SameSite=None; Secure` cookies **are** accepted on a top-level navigation response). No token ever appears in the redirect URL or fragment.
- `refresh`: reads `cp_rt` (its `Path` means it arrives only here), keeps the existing rotation and reuse → revoke-whole-family logic unchanged, sets the new `cp_at`/`cp_rt`, returns `{email, cf_handle}` only. Reuse still revokes the family and clears both cookies.
- `logout` / `logout-all`: revoke server-side (one token / all tokens, as today), then clear `cp_at`, `cp_rt`, `cp_tp`, `cp_csrf` with `Set-Cookie: <name>=; Max-Age=0` **repeating the exact `Path`, `SameSite` and `Secure` attributes** — RFC 6265bis: a deletion cookie that does not match the original's `Path`/`Domain` deletes nothing.
- New `GET /api/v1/auth/csrf` (Q4). No new dependencies — `secrets`, `hmac` are stdlib. CORS keeps the exact-origin list and `allow_credentials=True`; `X-CSRF-Token` must be in allowed headers if "all headers" is ever narrowed.

`AuthOut` becomes `{email, cf_handle}` — `access_token`, `refresh_token`, `token_type` are removed. The frontend is the only client; code still expecting tokens is broken by design.

## Frontend changes

- `api/client.ts`: every `fetch` uses `credentials: "include"` (without it, Fetch sends no cookies cross-origin — the most common cause of "cookies don't work"); mutations attach `X-CSRF-Token` from the in-memory token; boot calls `GET /auth/csrf` before the first mutation. 401 flow, same shape as today: on `401`, single-flight `POST /auth/refresh` (cookie-authenticated, CSRF-checked), retry once; if refresh returns `401`, the session is dead — clear in-memory state, redirect to login. A `403 csrf_check_failed` triggers one CSRF re-fetch + one retry, then surfaces.
- `hooks/useAuth.tsx`: boot is `api.me()` as today, but nothing stores tokens — `login/register/verifyEmail/verifyTotp/completeGoogleSignIn` call the endpoint, then `api.me()`. Delete every `localStorage.setItem("cp_access_token" | "cp_refresh_token", …)`.
- `components/layout.tsx`: `EventSource` with `{ withCredentials: true }`, no `?token=`; on stream `401`, close → refresh → re-open.
- `types`: `AuthOut` loses its token fields; add `CsrfResponse { csrf_token: string }`.
- **Live-session migration:** a session live during the deploy ends. Ship backend first, then frontend; in between, the old frontend's `Authorization` header is ignored and its localStorage tokens are worthless. On first load after deploy, the new frontend deletes `cp_access_token` and `cp_refresh_token` from localStorage unconditionally (a three-line boot cleanup, kept for one release), and the user logs in again — acceptable for a one-user app, stated here rather than hidden. Returning users see the login screen once, not an error.
- **PWA:** the service worker precaches the app shell only and never caches `/api` responses, so no cookie or CSRF token can be served stale from cache; the SSE bypass is unchanged.

## Q6 — Third-party cookies blocked: the honest answer

In prod, Vercel → Render cookies **are** third-party cookies. If the user blocks them (Chrome's direction of travel; Safari/Firefox already restrict them), the browser does not send `cp_at`/`cp_rt` — login appears to succeed and every subsequent call returns `401`, so the user sees an endless login loop. There is no honest in-design fallback: falling back to localStorage would reintroduce the exact XSS exposure this batch exists to remove, and a JS-visible token store is forbidden by constraint 1. What still works: nothing authenticated — the landing page and static shell load; every API call, the sync stream and the dashboard fail. The *real* fix is architectural: make the API first-party — a custom domain pair on one registrable domain (`app.…` + `api.…`, first-party `Lax` cookies) or a Vercel rewrite proxying `/api/*` to Render, making the backend same-origin. That proxy is the recommended follow-up, not a silent fallback smuggled into this batch. Until then, the frontend must detect the loop (two consecutive `401`s after a successful login) and show a plain message — "Sign-in needs third-party cookies allowed for cp-compass-api-1j9a.onrender.com" — instead of looping forever.

## Three likeliest production failures and their patches

1. **Cookies never arrive in prod.** Login returns 200, `me()` returns 401. Cause is almost always one of three: the frontend forgot `credentials: "include"`; the backend answered `Access-Control-Allow-Origin: *` (invalid with credentials — Fetch rejects the response); or `SameSite=None` was set without `Secure`. Patch: check all three in order; verify in DevTools that `Set-Cookie` carries `Secure; SameSite=None` and the cookie appears under the Render domain in Application → Cookies.
2. **CSRF 403s on every mutation after login.** Cause: the frontend kept a pre-login token after the login rotation, or two tabs raced a rotation. Patch: `client.ts` must replace its in-memory token after any auth-state change (or re-fetch `/auth/csrf`); rotation happens only on auth-state change — never per request — so tabs cannot desynchronise mid-session.
3. **Logout leaves the user logged in.** Cause: the clearing `Set-Cookie` omitted `Path=/api/v1/auth/refresh` (for `cp_rt`) or `Secure; SameSite=None`, so the browser kept the original cookie. Patch: build clear-cookie headers from the same helper that sets them, with identical attributes and `Max-Age=0`; verify in Application → Cookies after logout and confirm a post-logout `me()` returns 401.
