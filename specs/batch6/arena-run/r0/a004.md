# Arena a004 — Defense in depth: three independent CSRF layers, no single point of failure

**One line:** Cookie-only auth (`SameSite=None; Secure` prod / `Lax` dev) protected by *all three* CSRF layers — strict Origin/Referer allowlist, HMAC-bound double-submit token delivered by JSON echo, and a mandatory `X-CSRF-Token` header forcing a CORS preflight — so bypassing any one layer still leaves the other two holding.

## Layers that fail independently

Prod is cross-site (Vercel → Render), so `SameSite=None` is required — and therefore provides **zero** CSRF protection in prod. This design assumes SameSite contributes nothing in prod and builds two server-enforced layers independent of it. Each stops a distinct attack the others would let through:

| Layer | Attack it stops that the others miss | If it is removed / bypassed |
|---|---|---|
| **L1 — SameSite** (Lax dev, None prod) | Naive cross-site `POST` in dev: the browser withholds the cookie. | Prod: nothing changes. Dev: POSTs reach the server — caught by L2/L3. |
| **L2 — Origin/Referer allowlist** (server, exact match) | Attacker *knows* the token (leaked via logs/Referer). The browser still sets `Origin: https://evil.com`, unspoofable from a browser, so the request dies even with a valid token. Also stops top-level-GET CSRF. | A token leak becomes a full CSRF; a wildcarded allowlist becomes exploitable. |
| **L3 — Double-submit + custom header** | Origin is *absent or untrustworthy*: stripped by a privacy proxy, or the request comes from an allowed origin via an open redirect. The attacker cannot read the victim's token (same-origin policy) or forge one (HMAC-bound, §Q4). The header forces a CORS preflight, which a plain `<form>` POST cannot perform. | Stripped-Origin or allowed-origin requests pass the Origin check with no second proof. |

No layer trusts another: L2 does not assume the token is secret; L3 does not assume Origin is present; L1 is treated as already defeated in prod.

## Q1 — Cookie-only auth, no Authorization-header fallback

**Cookie-only. No fallback, no dual path.** `get_current_user` reads the access JWT from the cookie only (names below). It never reads `Authorization`, never accepts `?token=`. A fallback would reintroduce what N4 removes: a JS-readable token path and a way for a stolen localStorage token to still work. No cookie → 401. There are no non-browser callers.

## Q2 — CSRF mechanism: combination, exact request matrix

**All three: SameSite + Origin/Referer + double-submit.** Checked on **every non-safe method** — `POST`, `PUT`, `PATCH`, `DELETE` on every `/api/v1/*` route, no exceptions — including `/auth/login`, `/auth/register`, `/auth/verify-email`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/totp-verify`, `/auth/google/callback`, `/auth/refresh`, `/auth/logout`, `/auth/logout-all`. A mutation must pass **both** L2 and L3: (a) `Origin` (fallback `Referer` if `Origin` is absent) exactly matches the allowlist — prod `https://cp-compass-phi.vercel.app` only; dev `http://localhost:5173` and `http://localhost:4173` — never `*`, never suffix/prefix match; (b) `X-CSRF-Token` equals the `cp_csrf` cookie in constant time *and* passes the HMAC check (§Q4). Fail either → `403 {"detail":"csrf_failed"}`, with no distinction between which check failed (no probing oracle). If **both** `Origin` and `Referer` are absent on a mutation → reject (fail closed); the real frontend always sends `Origin` on a CORS `POST`.

**Exempt, and why each is safe:** `GET`/`HEAD`/`OPTIONS` — safe methods, no state change (no state-changing GETs exist). `GET /api/v1/auth/csrf` — only *issues* a token. Preflight `OPTIONS` — handled by CORS before auth, no credentials or body. `GET /api/v1/sync/stream` (SSE) — only reads the caller's own latest sync job; exempt from the *token* but **not** from L2: it still enforces the exact Origin allowlist plus CORS (exact `Allow-Origin`, `Allow-Credentials: true`).

## Q3 — SameSite: None+Secure in prod, Lax in dev

Prod: `SameSite=None; Secure` on every cookie — the only combination browsers accept cross-site. `Secure` is mandatory with `None`; without it the cookie is silently dropped. Dev: `SameSite=Lax`, **no** `Secure` — a `Secure` cookie is never sent over plain HTTP, and `None` without `Secure` is rejected, so `None` is unusable in dev. This only works if dev is genuinely same-site, so **change the dev backend host from `127.0.0.1:8004` to `localhost:8004`** (`VITE_API_URL=http://localhost:8004`): `localhost:5173` → `localhost:8004` is same-site (ports are ignored), while `localhost` → `127.0.0.1` is a different host and Lax cookies on cross-origin `fetch` are withheld. Reach the Vite preview on `[::1]:4173` as `http://localhost:4173`. One setting, `ENV=prod|dev`, drives a single `set_auth_cookies()` helper — never per-endpoint flag juggling.

## Q4 — CSRF token lifecycle

**Issued when:** lazily, on `GET /api/v1/auth/csrf` (called by `client.ts` on boot and before the first mutation if no token is in memory), and re-issued in the JSON body of every auth response (login, register, verify-email, totp-verify, Google callback, refresh). **Stored where:** the `cp_csrf` cookie (table below) **and** a module-level in-memory variable in `client.ts` only — never `localStorage`, `sessionStorage`, or any persisted JS variable. **Before the first mutation:** the frontend calls `GET /auth/csrf` with `credentials: "include"` *before* login/register/forgot/reset. Those are mutations too, so they are not exempt — a forged login (login CSRF, forcing the victim into the attacker's account) is blocked the same way.

**The cross-site trap:** JS on `vercel.app` *cannot* read `document.cookie` for an `onrender.com` cookie, so classic `document.cookie` double-submit fails in prod (it only works in dev, where both sides share `localhost`). The token therefore travels by **JSON echo**: `GET /auth/csrf` returns `{"csrf_token": "<value from the cookie>"}`; the frontend keeps it in memory and sends it as `X-CSRF-Token`. The cookie can therefore be `HttpOnly` too — XSS cannot read it via `document.cookie` even in dev. **Format:** `base64url(32 random bytes) + "." + HMAC-SHA256(SECRET_KEY, random + "|" + session_id)`, where `session_id` is the refresh-token family id once logged in, `"anon"` pre-login. The server verifies the HMAC and compares header-vs-cookie in constant time. Binding matters: without it, an attacker who can set a cookie on the victim (cookie-tossing) could set a *known* token cookie and send the same value in the header — double-submit defeated. **Rotated when:** on login, totp-verify, Google callback, and every refresh rotation; cleared on logout. Every rotating response returns the new value in JSON, `client.ts` overwrites its in-memory copy, and a `403 csrf_failed` triggers one refetch of `/auth/csrf` plus one retry.

## Q5 — SSE auth: cookie + EventSource withCredentials, drop `?token=`

**Cookie, `withCredentials: true`, delete the query-param path.** `layout.tsx` opens `new EventSource(url, { withCredentials: true })`; the backend reads the access cookie in `/sync/stream` exactly like `get_current_user`. `decode_access_token_query` is deleted, and any request still carrying `?token=` gets `400`, so a stale frontend fails loudly instead of silently leaking. A URL token lands in Render access logs, browser history, and the `Referer` header — the three places a bearer credential must never go. `EventSource` cannot set an `Authorization` header, but it *can* send cookies with `withCredentials`, and CORS (exact `Allow-Origin` + `Allow-Credentials`) still gates cross-origin reads. The service worker already bypasses `/api` and never caches responses, so no worker change is needed. If the cookie expires mid-stream, the server closes it with 401 and the frontend falls back to polling `GET /sync/status` with `fetch` + `credentials: "include"`.

## Q6 — Third-party cookies blocked: what breaks, honest fallback

**In prod the auth cookies are third-party cookies** (set by `onrender.com` while the top-level page is `vercel.app`). If the user blocks third-party cookies (Chrome "Block third-party cookies", Safari ITP, Firefox ETP), **all authenticated use breaks**: login appears to succeed — the server sets cookies the browser silently discards — then `api.me()` returns 401, the app redirects to login, and the user loops forever. SSE fails the same way. There is **no silent fallback**: no localStorage, no `Authorization` header, no token in a URL — each would violate constraint 1 and reintroduce the XSS theft N4 exists to remove. **What the user sees:** a plain-language banner, detected on boot (login succeeded but the immediate `api.me()` is 401 *and* a probe `GET /auth/csrf` shows no cookie was stored): "CP Compass needs cross-site cookies to stay signed in. Allow cookies for `cp-compass-api-1j9a.onrender.com` in your browser settings, then tap Check again." — with per-browser steps. **What still works:** the static shell, landing, and PWA install — nothing authenticated, no fake "logged in" state. **Real fix (not Batch 6):** a same-site setup — a custom domain for the API, or a Vercel rewrite proxying `/api/*` to Render — making the cookies first-party. Name it in code comments; do not build it now.

## Cookie table (one helper, `ENV`-driven)

| Cookie | Prod | Dev | Max-Age |
|---|---|---|---|
| `__Host-cp_access` / `cp_access` — access JWT | `HttpOnly; Secure; SameSite=None; Path=/` | `HttpOnly; SameSite=Lax; Path=/` (no `Secure`) | 900 (15 min) |
| `__Host-cp_refresh` / `cp_refresh` — opaque refresh | as above | as above | 604800 (7 days) |
| `__Host-cp_csrf` / `cp_csrf` — CSRF token | `HttpOnly; Secure; SameSite=None; Path=/` | `HttpOnly; SameSite=Lax; Path=/` | 604800, rotated on login/refresh |
| `__Host-cp_totp` / `cp_totp` — totp_pending JWT | as above | as above | 300, cleared on verify/fail |

`__Host-` prefix in prod (requires `Secure`, `Path=/`, no `Domain` — which is why `Path` is `/`, not `/api/v1`); plain names in dev, because `__Host-` requires `Secure`, impossible over HTTP. No `Domain` is ever set (host-only). `AuthOut` drops `access_token`/`refresh_token` and becomes `{email, cf_handle, csrf_token?, requires_totp?}`; tokens exist only as `Set-Cookie` headers.

## What changes

**Backend:** `set_auth_cookies()` / `clear_auth_cookies()` helpers (all `Set-Cookie` in one place); `get_current_user` reads the cookie, no header; `login`, `register`, `verify-email`, `totp-verify`, `google/callback`, `refresh` set cookies + return `csrf_token` in JSON (refresh keeps rotation + reuse → revoke-family, keyed on the refresh cookie); `logout` revokes one token *and* clears all four cookies with `Max-Age=0` and identical flags (a clear with mismatched flags silently fails); `logout-all` revokes all families + clears; new `GET /api/v1/auth/csrf`; `/sync/stream` reads the cookie, enforces Origin/CORS, rejects `?token=`; a CSRF middleware/dependency enforcing L2+L3 on non-safe methods; CORS stays exact-origin + `allow_credentials=True`.
**Frontend:** `api/client.ts` — `credentials: "include"` on every `fetch`, in-memory `csrfToken`, `ensureCsrf()` before mutations, 401 → `POST /auth/refresh` once → retry once, 403 `csrf_failed` → refetch token once → retry once; `hooks/useAuth.tsx` — boot is `api.me()`, login/register/verifyEmail/verifyTotp/completeGoogleSignIn store nothing and call `api.me()`; `components/layout.tsx` — `EventSource` with `withCredentials`, no `?token=`; `types` — `AuthOut` without tokens, new `CsrfResponse`; on boot, delete legacy `cp_access_token` / `cp_refresh_token` from `localStorage` *and* `sessionStorage`.

## Live session during deploy + three failure modes

**Live session:** interrupted once. Old localStorage tokens are valid but unread — the backend no longer accepts a header and no cookie exists — so the next request is 401 and the user logs in again. No data is lost; a running sync job continues server-side, the SSE stream drops and reconnects after re-login. Orphaned refresh families cannot be used and expire within 7 days. Returning users get legacy keys deleted on boot.
**1. Prod cookie silently dropped** (missing `Secure`, or a Vercel preview origin not allowlisted): symptom is login-loop 401s. Patch: inspect `Set-Cookie` in DevTools → Network, verify flags, confirm Render is HTTPS and the exact origin is allowlisted. **2. CSRF 403 loop after refresh rotation** (stale in-memory token): the `client.ts` refetch + retry-once handles it, and every refresh response returns the new token; if it still loops, log server-side whether header/cookie/HMAC mismatched (never the token value). **3. SSE 401 / stream never opens** (missing `withCredentials`, CORS `Allow-Origin: *`, or third-party cookies blocked): check `withCredentials` and the exact CORS headers, then fall back to `fetch` polling of `/sync/status` so sync progress still shows.
