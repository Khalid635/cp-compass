# Arena a002 — First-party cookies via a same-origin proxy, Lax everywhere, double-submit CSRF

## One-line decision
Cookie-only auth, no header fallback. Make the cookies first-party with a Vercel `/api` rewrite to Render, so `SameSite=Lax` works in prod and dev, Safari ITP and third-party-cookie blocking stop mattering, and old browsers that mishandle `SameSite=None` keep working. CSRF is double-submit + Origin/Referer allowlist, with missing-header tolerance for corporate proxies.

## Q1. Cookie-only auth, or cookie + Authorization-header fallback?
Cookie-only. No `Authorization: Bearer` fallback anywhere. A fallback reintroduces exactly what N4 removes: a token JS can read and exfiltrate after any XSS, plus a second auth path every endpoint must keep in sync. `get_current_user` reads one source only: the `cp_access` cookie. The only "fallback" is at the transport layer, not the credential layer: if the direct cross-site cookie path fails, the frontend switches its base URL to the same-origin proxy (see Q6) — the credential stays a cookie either way. Legacy `Authorization` parsing and `decode_access_token_query` are deleted, not deprecated.

## Q2. CSRF mechanism
Combination: double-submit as the primary gate, Origin/Referer as the second layer, `SameSite` as defence-in-depth only — never the sole check.

Checked: every state-changing request — `POST/PUT/PATCH/DELETE` on all `/api/v1/*`, including login, register, verify-email, forgot/reset password, totp-verify, refresh, logout, logout-all, and sync start/cancel. Pre-login mutations are checked too: login CSRF and password-reset CSRF are real attacks.

Check: (a) `X-CSRF-Token` header equals the `cp_csrf` cookie value, compared in constant time (`hmac.compare_digest`), both present and non-empty; (b) `Origin` (preferred) or `Referer` must be in the exact allowlist (`https://cp-compass-phi.vercel.app` in prod; `http://localhost:5173`, `http://localhost:4173`, `http://[::1]:5173` in dev) or match the request `Host` for same-origin proxy calls.

Missing-header tolerance (the compatibility point): corporate proxies, privacy extensions and old browsers strip `Origin`/`Referer`. If **both** are absent but double-submit passes, accept and log `csrf_origin_missing` (counter only, no PII). If either is present and mismatched, reject with 403 even if double-submit passes — a present header is never wrong by accident. Never gate on `Sec-Fetch-Site`: old browsers do not send it.

Exempt: `GET`/`HEAD`/`OPTIONS` (read-only), `GET /auth/csrf` (it only issues a token), and the Google OAuth callback `GET /auth/google/callback` (its protection is the HMAC-signed `state` + `code` already in place; no mutation happens until state verifies). SSE `GET /sync/stream` is exempt from the CSRF header check because `EventSource` cannot send custom headers — it is protected by the cookie + `SameSite=Lax`, and it exposes only the caller's own job and changes no state.

On failure: `403 {"detail": "csrf_failed"}`, no retry, no refresh attempt. The frontend shows "Security check failed — please reload" only for this code.

## Q3. SameSite policy
`Lax` everywhere; `None` is not used on the primary path at all. `SameSite=None` requires `Secure`, breaks on plain-HTTP dev, is rejected as third-party by Safari ITP and by any user blocking third-party cookies, and is mishandled by old browsers (Chrome <67, Safari 12, old embedded WebViews treat unknown `None` as `Strict`, silently killing auth). `Lax` is understood by every browser shipped in the last decade, survives ITP, and suffices once cookies are first-party. How they become first-party: add a Vercel rewrite in `vercel.json` — `{ "source": "/api/:path*", "destination": "https://cp-compass-api-1j9a.onrender.com/api/:path*" }` — and set the frontend API base to same-origin `/api` in prod. In dev, Vite proxies `/api` to `http://127.0.0.1:8004` (same for preview on `[::1]`), so dev is same-origin too. `Secure` is then simply on in prod (HTTPS) and off in dev (plain HTTP) — no `Secure`-on-HTTP bug, no dev-only flag drift. Direct cross-site calls to Render remain only as a degraded fallback, where `None`+`Secure` is used — and that path is expected to fail for ITP/blocked-cookie users, which is why it is the fallback, not the default.

## Q4. CSRF token lifecycle
Issued on `GET /api/v1/auth/csrf` (public, no auth, rate-limited like login), returning `{"csrf_token": "<32-byte urlsafe>"}` and setting the `cp_csrf` cookie; also piggybacked as `Set-Cookie` on `GET /auth/me` and on every login/register response, so a returning user rarely needs the extra round-trip. Stored as the `cp_csrf` cookie (NOT `HttpOnly`, so JS can read it) plus an in-memory copy in `client.ts`. Never in `localStorage`/`sessionStorage`.

The frontend gets it before the first mutation: `client.ts` boot runs `ensureCsrf()` — `GET /auth/csrf` with `credentials: "include"` — before any `POST`, including the login form submit; the login page calls it on mount, so the token is ready before the user can submit. If that call fails (offline/flaky mobile), the mutation is retried once after a second `ensureCsrf()`; after two failures the UI shows "Cannot reach the server — check your connection", not a CSRF error.

Rotated on login, logout, logout-all, and TOTP completion — never on refresh, never per-request. Per-request rotation breaks parallel fetches, double tabs and flaky-mobile retries (tab A rotates the token tab B just read). After rotation the previous token stays valid for 60 s (server keeps `prev_csrf` + expiry in the session row) so in-flight requests land. Generation: `secrets.token_urlsafe(32)` per rotation.

## Q5. SSE auth
Cookie + `EventSource` with `withCredentials: true`, over the same-origin proxy path. Delete `?token=` entirely and delete `decode_access_token_query`. `layout.tsx` opens `new EventSource("/api/v1/sync/stream", { withCredentials: true })`. A URL token lands in Render access logs, browser history, the `Referer` header, and paste accidents — a cookie sends nothing extra and is `HttpOnly`. Reconnect: `EventSource` auto-reconnects on drop, but a `401` means the access cookie expired, not a network blip — `layout.tsx` listens for `error`, calls the normal `POST /auth/refresh` (cookie + CSRF header) once, then reopens the stream once; a second failure closes it and shows "Live sync paused — sign in again" instead of reconnect-looping forever. The service worker already bypasses `/api`, so no worker change is needed; verify the proxy rewrite does not cache the stream (`Cache-Control: no-store` on the stream response).

## Q6. What breaks if the user blocks third-party cookies?
On the primary proxy path: nothing. The cookies are first-party (host `cp-compass-phi.vercel.app`), so "block third-party cookies", Safari ITP and Firefox Enhanced Tracking Protection do not touch them. That is the whole point of the proxy — the user sees normal login and normal sync. If the proxy is unavailable (Vercel rewrite misconfigured, or a future direct-origin deployment) and the frontend falls back to direct Render calls, then blocking third-party cookies breaks everything authenticated: login returns 200 and sets cookies the browser immediately discards, the next `GET /auth/me` returns 401, and the app would loop login → 401 forever. We prevent the loop with a probe: after login, `client.ts` calls `GET /auth/me`; if it 401s while login just succeeded, it calls `GET /auth/cookie-probe` (sets a throwaway cookie, reads it back) to confirm cookies are blocked, then shows a plain banner: "Your browser is blocking cookies for cp-compass-api-1j9a.onrender.com, so sign-in cannot stay on. Allow third-party cookies for this site, or use the main site address (not the API address directly)." What still works in that degraded state: the static PWA shell, landing page, and any public content. What does not: login persistence, dashboard, sync, SSE, logout — there is no honest read-only authenticated mode without a cookie. No token-in-URL or `localStorage` fallback is offered, even temporarily: a "temporary" fallback becomes the permanent hole. The real fix is restoring the proxy path, not weakening auth for one browser setting.

## Cookie table
| Cookie | Prod (proxy, HTTPS) | Dev (Vite proxy, HTTP) | Max-Age |
|---|---|---|---|
| `cp_access` | `HttpOnly; Secure; SameSite=Lax; Path=/`, host-only, no `Domain` | `HttpOnly; SameSite=Lax; Path=/` (no `Secure`) | 900 s |
| `cp_refresh` | `HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth` | same minus `Secure` | 604800 s (7 d) |
| `cp_csrf` | `Secure; SameSite=Lax; Path=/`, NOT `HttpOnly` | minus `Secure` | 604800 s |
| `cp_totp` (pending 2FA) | `HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth/totp-verify` | minus `Secure` | 300 s, cleared on verify/failure |

`Path=/api/v1/auth` on the refresh cookie means the browser only sends it to refresh/logout/logout-all — never on sync or data calls. No `Domain` is ever set: it would widen the cookie to subdomains that do not exist and confuse old browsers. On the direct-origin fallback path only, flags switch to `SameSite=None; Secure` with the same names and ages.

## Backend changes
- `get_current_user`: read `request.cookies["cp_access"]`, verify with the existing PyJWT HS256 decode; no `Authorization` parsing. Missing/invalid → 401 `{"detail": "not_authenticated"}`.
- `login`, `register`, `verify-email`, `totp-verify`, `google/callback`: stop returning tokens in JSON. Set `cp_access` + `cp_refresh` (and rotate `cp_csrf`) via `Set-Cookie`; return `AuthOut { email, cf_handle }` only — drop `access_token`, `refresh_token`, `token_type`. `totp-verify` consumes `cp_totp` and clears it. Google callback sets cookies on the redirect response to the frontend (same-origin proxy keeps `Set-Cookie` first-party); add `?oauth=ok` so the frontend knows to call `api.me()`.
- `POST /auth/refresh`: reads the `cp_refresh` cookie, rotates the refresh token, reuse → revoke the whole family (logic unchanged), sets new `cp_access` + `cp_refresh`; requires the CSRF check; does NOT rotate the CSRF token.
- `POST /auth/logout`, `/auth/logout-all`: revoke server-side (unchanged), then clear all four cookies with `Max-Age=0` and flags identical to the setter — a clear with mismatched `Path` silently fails, so the clear helper must take the same flag set as the setter.
- New `GET /auth/csrf` and `GET /auth/cookie-probe` (sets + reads a `cp_probe=1` cookie, returns `{"cookies_ok": bool}`). `GET /sync/stream`: cookie auth via `get_current_user`, no query token.
- CORS: `allow_origins` exact list and `allow_credentials=True` unchanged — with the proxy path the browser makes same-origin calls, so CORS is only exercised on the direct fallback. Verify `X-CSRF-Token` is in `allow_headers` (already `*`).

## Frontend changes
- `api/client.ts`: base URL becomes same-origin `/api` (`VITE_API_URL` override only for the direct fallback); `credentials: "include"` on every call; `ensureCsrf()` before mutations, sending `X-CSRF-Token` from the in-memory token (refreshed from `document.cookie` if empty); 401 → single-flight `POST /auth/refresh` → retry once (same shape, now cookie-driven); on 401-after-refresh, clear in-memory state and redirect to login. Fallback switch: if `cookie-probe` reports blocked, set base to Render and retry once, then show the Q6 banner.
- `hooks/useAuth.tsx`: boot is still `api.me()`; login/register/verifyEmail/verifyTotp/completeGoogleSignIn no longer store anything — they call `api.me()` after success. On mount, delete legacy keys `cp_access_token` and `cp_refresh_token` from `localStorage` unconditionally.
- `components/layout.tsx`: `EventSource` with `withCredentials: true` to the proxy path; 401 → refresh-then-reopen-once (Q5).
- Types: `AuthOut` loses `access_token`, `refresh_token`, `token_type`; add `CsrfResponse { csrf_token: string }`.

## Live session during deploy + legacy localStorage
A session live during the deploy is signed out — honestly and once. Its refresh token lived in `localStorage`, so there is no cookie to convert and no silent migration is possible; the backend stops accepting `Authorization` headers at deploy. The user sees the login page with "Signed out for a security upgrade — please sign in again." Tolerable for a one-user base; state it in the release note. Returning users: on first boot after deploy, `useAuth` deletes `cp_access_token` and `cp_refresh_token` from `localStorage` (and `sessionStorage` if present) before any network call, so no stale token ever leaves the browser again; the keys are never read. Old refresh tokens in an attacker's hands cannot be presented at all post-deploy, since no endpoint accepts them.

## Three most likely production failures + patches
1. **Vercel rewrite drops or caches `Set-Cookie` / the stream.** Symptom: login 200s but `api.me()` 401s even with cookies allowed. Patch: verify the rewrite preserves headers (no `Cache-Control` override on `/api/*`); add a deploy check that logs in via the proxy and asserts two `Set-Cookie` headers; if the rewrite cannot be fixed quickly, flip `VITE_API_URL` to direct Render with `None`+`Secure` as a documented degraded mode.
2. **Old browser / embedded WebView rejects the cookie or strips `Origin`.** Symptom: 403s on mutations in one browser only. Patch: the Q2 missing-header tolerance already covers stripped `Origin`; for a browser that rejects the cookie itself, the probe banner names the browser and the fix (update it, or allow cookies for the site). Never "fix" it by re-adding a header fallback.
3. **CSRF rotation race across two tabs.** Symptom: one tab's mutation 403s right after login in another tab. Patch: the 60 s previous-token grace in Q4 covers it; if reports persist, extend grace to 300 s and add a `403 csrf_failed` → `ensureCsrf()` → retry-once path in `client.ts` for mutations only (never for refresh).
