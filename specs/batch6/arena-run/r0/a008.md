# Arena a008 — Deploy it like a 3am incident: cookie-only auth with a rehearsed rollback

## The six decisions

1. **Cookie-only, no Authorization-header fallback.** One auth path. A fallback keeps the XSS token-theft hole this batch exists to close, and lets a stale frontend silently keep working on Bearer tokens. `get_current_user` reads `request.cookies["cp_access"]` only; any `Authorization` header is ignored.
2. **CSRF = double-submit cookie + Origin/Referer check, both enforced.** SameSite alone is not enough: prod cookies are `SameSite=None`, so they are sent cross-site by design. Every `POST`/`PUT`/`PATCH`/`DELETE` must carry `X-CSRF-Token` equal (constant-time `hmac.compare_digest`) to the `cp_csrf` cookie, and have `Origin` (fallback `Referer`) in the exact CORS allow-list. Exempt: `GET`/`HEAD`/`OPTIONS`, `GET /api/v1/auth/csrf`, `GET /api/v1/sync/stream` — all read-only. The stream is also Origin-checked and exposes only the caller's own latest sync job, so a cross-site `GET` can only show the victim their own data.
3. **SameSite: `None; Secure` in prod, `Lax` (no `Secure`) in dev — and fix the dev hostnames.** `SameSite=None` without `Secure` is rejected by modern browsers, and plain-HTTP localhost cannot set `Secure`. In dev, `Lax` works only because port does not matter to same-site: `localhost:5173` to `localhost:8004` is same-site. The current dev address `127.0.0.1:8004` breaks this — `localhost` vs `127.0.0.1` is cross-site — so dev must use `VITE_API_URL=http://localhost:8004` (the backend still binds `127.0.0.1:8004`; the name is what matters). No `Domain` anywhere: host-only cookies stay pinned to `cp-compass-api-1j9a.onrender.com` / `localhost`.
4. **CSRF lifecycle: stateless, issued before login, rotated only on auth transitions.** `GET /api/v1/auth/csrf` sets `cp_csrf` (32 random bytes, `secrets.token_urlsafe(32)`) and returns `{csrf_token}`; the frontend also reads it from `document.cookie`. Issued on app boot, on every login/register/forgot/reset response, and on logout (so a logged-out token cannot be replayed into a new session). **Not** rotated per request — that races parallel fetches and the single-flight refresh. No server state: the server only compares header vs cookie.
5. **SSE: cookie + `EventSource(url, {withCredentials: true})`, `?token=` deleted.** `decode_access_token_query` and the `?token=<jwt>` path are removed entirely. Cookies are sent because CORS is `allow_credentials=True` with an exact `Access-Control-Allow-Origin` (never `*`). The stream reads `cp_access` from cookies and Origin-checks the request.
6. **Third-party cookies blocked: honest failure, no silent fallback.** No localStorage fallback — that would reintroduce the vulnerability and violate constraint 1. What the user sees: login appears to succeed, then `api.me()` returns 401 and the app drops back to login. The frontend detects this shape (login 200 + immediate `me()` 401) and shows a persistent banner naming the backend host with per-browser allow steps (Chrome: Settings, Privacy, Third-party cookies, Allow `https://cp-compass-api-1j9a.onrender.com`; Firefox/Safari equivalents). What still works: the public landing page only; every authenticated call, sync, and the SSE stream fail. The real fix — a same-domain backend via a Vercel rewrite or custom domain — is follow-up work, not smuggled into Batch 6.

## Cookies (no `Domain` anywhere)

| Cookie | Prod | Dev | Max-Age |
|---|---|---|---|
| `cp_access` | `HttpOnly; Secure; SameSite=None; Path=/` | `HttpOnly; SameSite=Lax; Path=/` | 900 |
| `cp_refresh` | `HttpOnly; Secure; SameSite=None; Path=/api/v1/auth/` | `HttpOnly; SameSite=Lax; Path=/api/v1/auth/` | 604800 |
| `cp_csrf` | **not** `HttpOnly`; `Secure; SameSite=None; Path=/` | not `HttpOnly`; `SameSite=Lax; Path=/` | 86400 |
| `cp_totp` | `HttpOnly; Secure; SameSite=None; Path=/api/v1/auth/totp-verify` | `HttpOnly; SameSite=Lax; Path=/api/v1/auth/totp-verify` | 300 |

`cp_refresh` is path-scoped to `/api/v1/auth/` so it is only sent to refresh/logout/logout-all, never on ordinary calls. `cp_totp` is path-scoped to its verify endpoint. Clear with `Max-Age=0` plus identical `Path`/`SameSite`/`Secure` — a clear with the wrong `Path` silently fails to delete.

## Backend changes (FastAPI, no new dependencies)

- `get_current_user`: reads `cp_access` from `request.cookies`, `jwt.decode` (HS256) as today; no `Authorization` parsing. On failure, 401 with `X-Auth-Mode: cookie`, so a stale frontend (or a human debugging at 3am) can tell which auth mode the backend speaks.
- `login`: success sets `cp_access` + `cp_refresh` + fresh `cp_csrf`; returns `AuthOut` **without tokens**: `{email, cf_handle}`. With TOTP enabled: sets only `cp_totp` + fresh `cp_csrf`, returns `{totp_required: true, email}`. Lockout and per-IP budget unchanged, applied before any cookie is set.
- `verify-email`, `forgot`, `reset`: CSRF-checked mutations; set/refresh `cp_csrf` on response. Recovery still returns JSON messages only, no tokens.
- `totp-verify`: reads `cp_totp` (not a JSON field), verifies the code, sets `cp_access` + `cp_refresh`, clears `cp_totp` (`Max-Age=0`, same `Path`). Missing/expired `cp_totp` returns 401 `totp_session_expired`; the user re-enters their password.
- `google callback`: as `login` — sets cookies, redirects to the Vercel frontend with **no token in the URL**. If TOTP is enabled for that Google account, set `cp_totp` and redirect to `/login?totp=1`.
- `refresh`: CSRF-checked; reads `cp_refresh`; rotation plus reuse-revokes-whole-family unchanged, on the server-side family in Neon. On reuse, revoke the family **and** clear all three auth cookies. Returns `{email, cf_handle}` only, plus fresh cookies.
- `logout`: revokes that refresh token server-side, clears `cp_access`/`cp_refresh`/`cp_totp`, rotates `cp_csrf`. `logout-all`: revokes all families, clears the same cookies.
- `GET /api/v1/auth/csrf`: issues `cp_csrf` + `{csrf_token}`; lightly rate-limited (in-memory limiter is fine on one worker).
- `GET /api/v1/sync/stream`: cookie auth via `get_current_user`, Origin in the allow-list, no `?token=` — a request carrying one gets 400, failing loud so nothing silently depends on the old path.

```python
def _set_auth_cookies(resp, access, refresh):
    resp.set_cookie("cp_access", access, httponly=True, secure=IS_PROD,
        samesite="None" if IS_PROD else "Lax", path="/", max_age=900)
    resp.set_cookie("cp_refresh", refresh, httponly=True, secure=IS_PROD,
        samesite="None" if IS_PROD else "Lax", path="/api/v1/auth/", max_age=604800)

async def require_csrf(request: Request):  # every POST/PUT/PATCH/DELETE
    if request.method in ("GET", "HEAD", "OPTIONS"): return
    origin = request.headers.get("origin"); ref = request.headers.get("referer")
    if origin and origin not in ALLOW_ORIGINS: raise HTTPException(403, "bad_origin")
    if not origin and ref and urlparse(ref).netloc not in ALLOW_HOSTS: raise HTTPException(403, "bad_referer")
    if not origin and not ref: raise HTTPException(403, "missing_origin")
    token = request.headers.get("x-csrf-token", "")
    if not token or not hmac.compare_digest(token, request.cookies.get("cp_csrf", "")):
        raise HTTPException(403, "bad_csrf")
```

## Frontend changes

- `api/client.ts`: every `fetch` gets `credentials: "include"`; the `Authorization` header and all `localStorage` token reads are deleted. `getCsrf()` reads `cp_csrf` from `document.cookie` and sends `X-CSRF-Token` on every mutation. Boot calls `GET /auth/csrf` before the first mutation. On 401: single-flight `POST /auth/refresh` (with CSRF header — the cookie is still readable after a 401), then retry once; if refresh 401s, redirect to login. On 403 `bad_csrf`: fetch a fresh CSRF token once, retry once, then surface the error. Never store any token in a JS variable across reloads.
- `hooks/useAuth.tsx`: boot is `api.me()` with cookies; `login`/`register`/`verifyEmail`/`verifyTotp`/`completeGoogleSignIn` store nothing — they set state from `{email, cf_handle}` and call `api.me()`. On first boot of the new build, delete legacy keys `cp_access_token` and `cp_refresh_token` (and any `totp_pending`) from `localStorage` **before** `me()`, so a downgraded or rolled-back page cannot resurrect them.
- `components/layout.tsx`: `new EventSource(url, {withCredentials: true})`; remove the `?token=` construction. On `onerror` with a 401-shaped close, stop retrying and show "session expired — log in again".
- `types`: `AuthOut` becomes `{email: string; cf_handle: string | null; totp_required?: boolean}`; delete token fields everywhere.

## Live-session migration

One live user (the owner) makes this survivable but not free. The deploy is a hard cutover: the moment the new backend is live, **every existing session dies** — old tokens live only in `localStorage`, the new backend ignores them, and there is no cookie to fall back on. Mid-sync, the sync job survives in Neon and re-attaches after he logs in again; the SSE stream drops and reconnects. Between login step 1 and TOTP step 2, the 5-minute `totp_pending` JWT is worthless and he re-enters his password. Tell him before the deploy: "you will be logged out once; log in again; nothing else is lost." Legacy keys are wiped by the new frontend on boot; a returning user on an old cached tab is logged out, not silently migrated. Deploy when he is not in a contest or a sync — not at 3am, not mid-tournament.

## Deploy and rollback runbook (Render free + Vercel)

Render free has one worker, slow cold starts (expect 30–60 s+ of 502/empty replies while the new worker boots), and no zero-downtime deploy. Vercel deploys in seconds. **Order: backend first, frontend second, inside one short window (under 10 min), announced to the owner.** Either order is broken during the skew, so pick the safe brokenness: new backend + old frontend fails *closed* (old frontend sends `Bearer`, gets 401, shows login — no tokens are issued, nothing leaks). New frontend + old backend would fail while the old backend still returns JSON tokens the new frontend drops — also broken, but it briefly keeps the old token-issuing code live. Do not ship a "compatibility shim" accepting `Bearer` for a transition period: it defeats the migration and will be forgotten in place.

**Rollback (if cookies break login):** Render dashboard, previous deploy, Rollback/Redeploy previous commit; then Vercel, previous deployment, Promote. Backend first again, so the two agree. **Does rollback re-admit localStorage tokens? Only if they are still there.** If the new frontend already ran in his browser, it wiped `cp_access_token`/`cp_refresh_token` on boot — rollback restores the old code but the tokens are gone, so he must log in again (the refresh family is still in Neon, but its token value was in the wiped localStorage — unrecoverable by design). If rollback happens before the new frontend ever loaded, the old tokens are intact and the old session resumes. Never add a "convert cookie back to JSON token" endpoint to make rollback smoother; that is a token-exfiltration endpoint wearing a runbook costume. Rollback rule: if login is broken for more than 10 minutes after the new backend is warm, roll back — do not debug CSRF flags against a live broken login.

**Split-deploy skew:** Render-new + Vercel-old means login 401s, dashboard shows logged-out, sync/SSE dead; the fix is to finish the Vercel deploy, not to touch the backend. Vercel-new + Render-old means `me()` and refresh 401 (the old backend wants `Bearer`); the fix is to finish the Render deploy. In both cases the PWA service worker can prolong the skew: it precaches the app shell, so a cached old shell keeps running old auth after the new deploy. Bump the SW cache version / `BUILD_ID` in the same release and call `skipWaiting()` so the new shell activates on next load; verify the live shell's `BUILD_ID` matches the deployed commit.

## Live verification checklist (against prod, in order)

1. Cold start: `curl -s -o /dev/null -w "%{http_code} %{time_total}\n" https://cp-compass-api-1j9a.onrender.com/api/v1/health` — expect 200 after the worker warms; record the time.
2. Login with a cookie jar: `curl -c jar.txt -b jar.txt -X POST …/auth/login -d '{"email":…, "password":…}'` — assert the body contains **no** `access_token`/`refresh_token`, and `Set-Cookie` shows `cp_access … HttpOnly; Secure; SameSite=None`, `cp_refresh … Path=/api/v1/auth/`, `cp_csrf` **without** `HttpOnly`.
3. `curl -b jar.txt …/auth/me` returns 200; with no jar, 401.
4. CSRF negatives: mutation with jar but **no** `X-CSRF-Token` returns 403; wrong token 403; `Origin: https://evil.example` 403. With the token from `cp_csrf`, 200.
5. Refresh: `POST …/auth/refresh` with jar + CSRF header returns 200 and a **changed** `cp_refresh`; replay the old `cp_refresh` returns 401 and revokes the family (verify on a throwaway session: the next `me()` with the new cookie also 401s).
6. SSE: open the stream in the browser with devtools Network open — confirm the request carries `Cookie: cp_access=…` and no `?token=` in the URL, and sync progress events arrive.
7. Logout: `POST …/auth/logout` returns `Set-Cookie` for all three auth cookies with `Max-Age=0`; `me()` after returns 401; the revoked refresh token reused returns 401.
8. TOTP: login with a TOTP account sets only `cp_totp`, `me()` 401s; wrong code 401s; right code sets the auth cookies and clears `cp_totp`.
9. Google OAuth: complete a sign-in, confirm the redirect URL contains no token and the landing page loads authenticated.
10. Skew check: Vercel's served JS contains `credentials: "include"` and no `cp_access_token` string, and the SW `BUILD_ID` equals the deployed commit.

## Three most likely production failures + patches

1. **Third-party cookies blocked (Safari ITP / hardened Chrome/Firefox).** Symptom: login 200, `me()` 401, infinite login loop. Patch: none in Batch 6 — the banner (decision 6) is the patch; the structural fix is a same-domain backend (Vercel rewrite to Render or a custom domain) in a follow-up.
2. **Stale PWA shell / split-deploy skew.** Symptom: after deploy, the app still sends `Bearer` or still builds `?token=` URLs. Patch: bump SW cache version + `BUILD_ID`, `skipWaiting()`, hard-refresh; if the old shell persists, unregister the service worker from devtools and reload. Prevention: checklist step 10.
3. **CSRF token desync across tabs / after login rotation.** Symptom: a tab opened before login mutates with the pre-login `cp_csrf` and gets 403. Patch: the client's one-retry rule (fetch fresh `/auth/csrf`, retry once) covers it; if it recurs, `useAuth` re-fetches CSRF after every `login`/`logout` transition and broadcasts it via `BroadcastChannel("cp-csrf")` so other tabs re-read the cookie before their next mutation. Never "fix" it by exempting an endpoint from CSRF.
