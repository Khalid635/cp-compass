# Arena a007 — Cookie-only + triple-lock CSRF (Origin + double-submit + SameSite=None), SSE by cookie, no fallback, no ?token=

## Verdict

Cookie-only auth. No `Authorization` fallback, no `?token=` anywhere.
Every state-changing request must pass **all three** checks: (1)
`Origin` on the exact allowlist, (2) double-submit CSRF token
(`X-CSRF-Token` header equals the `cp_csrf` cookie), (3)
`SameSite=None; Secure` cookies in prod. Each check alone is breakable
in this app; together they survive every attack below except XSS — and
no CSRF design stops XSS, so this design minimises what XSS can steal
(see "Best attack on my own design"). `SameSite=None` is *not* a
defence in prod: it is the price of cross-site cookies.

## Attacks that kill every rejected option

**Cookie-only, no CSRF.** Victim logged in, visits `evil.com`, which
auto-submits `<form action="https://cp-compass-api-1j9a.onrender.com/api/v1/auth/logout-all" method="POST">`.
The browser attaches the victim's cookies automatically — no CORS
preflight needed for a form POST. The server sees an authenticated
`logout-all` and revokes the whole refresh-token family. Same form
works against any POST mutation. Cookie-only without CSRF is not a
design, it is an invitation.

**Cookie + `Authorization`-header fallback.** This reintroduces the
disease HttpOnly cookies cure. The frontend must keep a token in
JS-readable storage to send the header. One stored-XSS hole — e.g. a
malicious Codeforces handle rendered unsanitised — and attacker JS
reads `localStorage.getItem('cp_access_token')` and posts it to
`evil.com`. The attacker replays it from curl, any IP, for 15 minutes,
with no browser, no cookie, no CSRF token and no Origin check in the
way. It also creates a precedence bug in `get_current_user`: if header
and cookie disagree (revoked cookie, live header), whichever the code
checks first silently wins, and logout can clear the cookie while the
header token keeps working. Rejected: the server never reads an
`Authorization` header.

**Double-submit cookie alone.** The token lives in a non-HttpOnly
cookie precisely so JS can read it — so any XSS reads it too. Attacker
JS does `document.cookie`, then
`fetch('/api/v1/auth/logout-all', {method:'POST', credentials:'include',
headers:{'X-CSRF-Token': stolen}})`. Header equals cookie, check
passes. Second failure: if the token is not bound to the login
session, it is a fixation token — an attacker fetches their own
`/auth/csrf`, plants that cookie on the victim, and the victim logs
in under an attacker-known CSRF token. That is why my design rotates
the token on login and binds it to the session. Double-submit alone
is a speed bump for XSS and a fixation risk; acceptable only as one
layer of three.

**Origin-only.** The hole is `Origin: null`. A sandboxed iframe
(`<iframe sandbox="allow-scripts allow-forms">`) or a `file://` page
makes the browser send `Origin: null`. If the server allowlists `null`
— or *permits a missing/null Origin* so "non-browser clients don't
break" — the attacker's form POST from that iframe passes with the
victim's cookies attached. Origin alone also does nothing against a
same-site attacker or any mutation ever exposed as GET. Good layer,
voided by one missing-header exception. My design rejects missing/null
Origin on mutations, no exceptions (curl has no victim cookies, so it
needs no carve-out).

**SameSite-only.** In prod this is vacuous: cross-site cookies *require*
`SameSite=None`, which means the cookie is sent on every cross-site
request, including the attacker's form POST. `SameSite=Lax` would block
the cross-site POST, but it would also block the legitimate app — the
frontend is on Vercel, the API on Render, so Lax cookies are simply
not sent with the app's own `fetch(..., {credentials:'include'})`.
Any design claiming "SameSite protects us" in this deployment has not
understood its own topology.

**Keeping `?token=` for SSE.** The access JWT in a URL leaks three
ways at once: Render access logs, browser history, and the `Referer`
header sent to any external site clicked while the stream URL is live.
Anyone recovering that string replays it with curl against any API
endpoint for 15 minutes, bypassing HttpOnly entirely. It defeats the
whole migration: the token the cookies were meant to hide is printed
in the network tab instead. Rejected; the stream authenticates by
cookie (Q5).

## The six questions, decided

**Q1 — Cookie-only, no fallback.** `get_current_user` reads exactly
one source: the access cookie. No header, no query param, no body
token. Logout, revocation and rotation all operate on cookies.

**Q2 — CSRF: Origin + double-submit + SameSite, all three, always.**
Checked on **every** POST/PUT/PATCH/DELETE under `/api/v1`, including
pre-login mutations (`login`, `register`, `forgot-password`,
`reset-password`, `verify-email`, `totp-verify`, `refresh`, `logout`,
`logout-all`, `complete-google-sign-in`). The check: (a) `Origin`
present and exactly equal to `https://cp-compass-phi.vercel.app`
(prod) or `http://localhost:5173` / `http://localhost:4173` (dev);
`Referer` is consulted only for same-origin GETs, never for mutations;
a missing, `null`, or non-listed `Origin` on a mutation is a 403, no
exceptions; (b) `X-CSRF-Token` header present and equal, by
constant-time compare, to the `cp_csrf` cookie. Exempt: GET/HEAD/OPTIONS
only — and only because no GET in this app changes state (audit this
in the build: `logout`, `refresh`, `verify-email` are all POST; any GET
that ever mutates moves behind the check). `/api/v1/sync/stream`
(GET) is exempt from the token check because EventSource cannot send
a custom header, but *not* from the Origin check (Q5).
`GET /auth/csrf` is exempt from the token check because it issues the
token; it is CORS-gated to the exact allowlist, so a foreign origin
cannot read its response. The Google OAuth callback GET is exempt (a
redirect, not a fetch); it is protected by the existing HMAC-signed
`state` parameter and sets cookies, never tokens.

**Q3 — SameSite: `None` in prod *and* dev, `Secure` in prod only.**
Prod: `SameSite=None; Secure` on every cookie — required, since
Vercel -> Render is cross-site. Dev: `SameSite=None` with `Secure`
**off**. This works because Chrome and Firefox treat
`http://localhost` and `http://127.0.0.1` as secure contexts and accept
`SameSite=None` without `Secure` there; it is the only flag combination
that lets Vite (`:5173`, `:4173`) send cookies to `127.0.0.1:8004`.
If a browser ever rejects it, the dev fallback is the Vite proxy
(`server.proxy: {'/api': 'http://127.0.0.1:8004'}`), making calls
same-origin — a dev-only escape hatch, not a second prod design.
`Secure` is driven by one env var (`ENV=prod|dev`), never by sniffing
the request scheme.

**Q4 — CSRF token lifecycle.** Issued by `GET /api/v1/auth/csrf`,
which sets the `cp_csrf` cookie and returns the same value as JSON
`{"csrf_token": "..."}`. Value: 32 random bytes,
`secrets.token_urlsafe(32)`. It is **bound to the session**: the server
stores only its hash in the refresh-family row, so a token issued
before login cannot be carried into a logged-in session. Rotated on:
login, logout, `totp-verify`, Google callback completion, `logout-all`.
**Not** rotated on silent `refresh` — rotating every 15 minutes
creates a multi-tab race where tab A refreshes and tab B's in-memory
token goes stale, so its next mutation 403s. Stored: in the `cp_csrf`
cookie (not HttpOnly, by design) *and* in a module-level JS variable
in `client.ts` (memory only, never localStorage/sessionStorage, never
a global). The frontend gets it before the first mutation by calling
`/auth/csrf` at boot (single-flight promise in `client.ts`); every
mutation awaits that promise first, so `login`/`register`/`forgot`/
`reset` all carry a valid token even pre-login. On a 403 with
`{"detail": "csrf_mismatch"}`, the client refetches `/auth/csrf` once
and retries once, then surfaces the error.

**Q5 — SSE: cookie + `EventSource` with `withCredentials`, `?token=`
deleted.** `layout.tsx` opens
`new EventSource('https://cp-compass-api-1j9a.onrender.com/api/v1/sync/stream',
{withCredentials: true})`. The backend drops `decode_access_token_query`
entirely; `/sync/stream` uses the same cookie `get_current_user` as
every other endpoint, plus an Origin check (exact allowlist, missing
Origin = 403) — this is what stops a foreign site opening the victim's
stream, because EventSource is CORS-gated and the browser will not
deliver a cross-origin stream without a matching
`Access-Control-Allow-Origin`. Any request still carrying `?token=`
gets a 400, so a stale frontend fails loudly instead of silently
leaking a token. Response headers: `Cache-Control: no-store`,
`X-Accel-Buffering: no`.

**Q6 — Third-party cookies blocked: auth breaks, and there is no token
fallback.** In prod the API cookie is a third-party cookie (set by
Render, read on a Vercel page), so a user blocking third-party cookies
sees this: login returns 200, the `Set-Cookie` is silently dropped,
the next `api.me()` is a 401, and the UI loops back to login. The
frontend detects "login 200 then immediate 401" and shows a banner:
*"Signed in, but your browser blocked CP Compass cookies. Allow cookies
for cp-compass-api-1j9a.onrender.com (Chrome: lock icon -> Site
settings -> Cookies -> Allow), then sign in again."* What still works:
the public landing page and nothing authenticated — no sync, no
dashboard, no recommendations. The fallback is **not** a token in
localStorage, because that hands the XSS attacker exactly what the
migration took away. A same-domain proxy would fix this properly, but
it is new infrastructure, out of scope for this batch; recorded here
as the follow-up, not smuggled in as a fallback.

## Cookies (exact)

| Cookie | Prod | Dev | Path | Max-Age |
|---|---|---|---|---|
| `__Host-cp_access` | HttpOnly, Secure, SameSite=None | `cp_access`, HttpOnly, SameSite=None, no Secure | `/api/v1` | 900 (15 min) |
| `__Host-cp_refresh` | HttpOnly, Secure, SameSite=None | `cp_refresh`, HttpOnly, SameSite=None, no Secure | `/api/v1` | 604800 (7 days) |
| `cp_csrf` | **not** HttpOnly, Secure, SameSite=None | not HttpOnly, SameSite=None, no Secure | `/` | 3600 |
| `__Host-cp_totp` | HttpOnly, Secure, SameSite=None | `cp_totp`, HttpOnly, SameSite=None, no Secure | `/api/v1/auth/totp-verify` | 300 (5 min) |

`__Host-` prefix in prod only: it forbids a `Domain` attribute and
forces `Path=/` semantics, killing cookie-tossing from any subdomain;
it requires `Secure`, so dev uses the bare names. The refresh cookie
is deliberately **not** restricted to `/api/v1/auth/refresh`: `logout`
needs it to revoke the right token, and a path-restricted cookie would
not be sent there. The TOTP cookie *is* path-restricted, because only
`totp-verify` ever needs it. Clearing a cookie means re-setting it
with the same name, Path, SameSite and Secure flags and `Max-Age=0` —
a clear with mismatched flags silently leaves the cookie alive, a
classic logout bug.

## Backend changes

- `get_current_user`: read the access cookie, `decode_access_token`;
  no header, no query. 401 if missing/invalid.
- `login`, `register`, `verify-email`, `totp-verify`, Google callback,
  `refresh`: on success, `Set-Cookie` access + refresh (+ rotate
  `cp_csrf` on login/totp/Google, not on refresh) and return `AuthOut`
  **without tokens**: `{"email": ..., "cf_handle": ...}`. The old
  `access_token` / `refresh_token` / `token_type` fields are deleted
  from the schema — a client still reading them gets nothing.
- `refresh`: reads the refresh cookie, rotates exactly as today; reuse
  of an already-rotated token revokes the whole family (DB logic
  unchanged — the family id lives in the DB row, not the cookie, so
  rotation semantics survive the transport change).
- `logout` / `logout-all`: require the CSRF check, revoke in the DB,
  then clear all four cookies with `Max-Age=0` and matching flags.
- New `GET /api/v1/auth/csrf`: issues the token as above; rate-limited
  like login (in-memory limiter is fine — one Render worker).
- `/sync/stream`: cookie auth + Origin check, `?token=` -> 400,
  delete `decode_access_token_query`.
- Enforce CSRF with **middleware**, not per-route decorators: a
  forgotten decorator on a new endpoint is a CSRF hole; a forgotten
  middleware exemption is a loud 403. Exempt list: GET/HEAD/OPTIONS,
  the OAuth callback, `/auth/csrf`.

```python
ALLOWED_ORIGINS = {"https://cp-compass-phi.vercel.app"}  # + localhost in dev
if request.method in ("POST", "PUT", "PATCH", "DELETE"):
    if request.headers.get("origin") not in ALLOWED_ORIGINS:
        return JSONResponse({"detail": "bad_origin"}, status_code=403)
    token = request.headers.get("x-csrf-token", "")
    if not token or not hmac.compare_digest(token, request.cookies.get("cp_csrf", "")):
        return JSONResponse({"detail": "csrf_mismatch"}, status_code=403)
```

## Frontend changes

- `api/client.ts`: `credentials: 'include'` on every fetch; drop all
  token storage and the `Authorization` header; add a module-level
  `csrfToken` (memory only) + single-flight `ensureCsrf()` calling
  `GET /auth/csrf`; every mutation awaits it and sends `X-CSRF-Token`.
  401 flow, unchanged in shape: single-flight `POST /auth/refresh`
  (with the current CSRF token — refresh is a mutation, so it needs
  one), then retry the original request once; a second 401 means
  "logged out". A 403 `csrf_mismatch` refetches the token and retries
  once.
- `hooks/useAuth.tsx`: boot is still `api.me()`; `login` / `register` /
  `verifyEmail` / `verifyTotp` / `completeGoogleSignIn` no longer store
  anything — they call the endpoint, then `api.me()`.
- `components/layout.tsx`: `new EventSource(url, {withCredentials: true})`,
  no token in the URL; on 401 the stream closes and the UI shows
  "signed out".
- `types`: `AuthOut` loses `access_token`, `refresh_token`,
  `token_type`. Any code referencing them fails the TypeScript build —
  that is the point; grep must find zero references.

## Migration: live sessions and legacy keys

A session live during the deploy dies once: the new backend no longer
reads `Authorization`, so old localStorage tokens stop working at the
moment of deploy, and the user signs in again. Acceptable for a
one-user app, and stated here, not hidden. On boot the frontend
deletes the legacy keys outright —
`localStorage.removeItem('cp_access_token')` and
`localStorage.removeItem('cp_refresh_token')` — before any network
call, so a returning browser never holds a stealable token again. The
PWA service worker needs no change: it never cached `/api` responses,
and the SSE stream already bypasses it.

## Best attack on my own design, and its patch

**XSS defeats all three CSRF layers at once.** Attacker JS running in
the app's origin reads the non-HttpOnly `cp_csrf` cookie, and every
`fetch` it makes carries the legitimate `Origin` header, because the
request genuinely originates from the victim's page. Origin check:
passes. Double-submit: passes. SameSite: irrelevant. The attacker can
call any mutation as the victim for as long as the tab is open. The
patch is not a fourth CSRF check — none survives in-origin JS. It is
(a) **limit what XSS can steal**: the access and refresh tokens are
HttpOnly, so unlike the localStorage design the attacker gets no
credential to replay from curl after the tab closes; the damage ends
when the session ends; (b) **shrink the XSS surface**: tighten CSP
beyond the current headers to `script-src 'self'` with no
`unsafe-inline`/`unsafe-eval`, and sanitise every Codeforces-derived
string (handle, problem title, verdict text) before render;
(c) **step-up for destructive actions**: `logout-all` (and any future
delete-account) requires the password again, so an XSS that can
already act as the victim still cannot nuke the account in one silent
call. XSS is the residual risk of every cookie design; this design
makes it transient instead of persistent, and says so.

## Three most likely production failures, and the patch for each

1. **Login loop — cookies rejected.** Login 200, `me()` 401, forever.
   Cause: `SameSite=None` without `Secure` rejected by a strict
   browser, `__Host-` set over plain HTTP in a misconfigured env, or
   clock skew. Patch: verify in DevTools that the `Set-Cookie` header
   carries the exact flags for the environment; show the
   third-party-cookie banner from Q6 instead of looping; never "fix"
   it by dropping to `SameSite=Lax` in prod, which would silently
   break all authenticated fetches.
2. **403 `csrf_mismatch` on the first mutation after login.** Cause:
   the frontend fired the mutation before `ensureCsrf()` resolved, or
   the login rotation raced a parallel mutation. Patch: mutations
   await the single-flight CSRF promise (never fire-and-forget it),
   and the client retries once after refetching on `csrf_mismatch`.
   Log whether the cookie or the header was missing — never the token
   value.
3. **SSE stream 401s while the REST API works.** Cause: `EventSource`
   created without `withCredentials: true`, or the Origin check on
   `/sync/stream` rejecting the Vercel origin after a deploy changed
   it. Patch: `layout.tsx` must pass `withCredentials`; the stream's
   Origin allowlist must be the same constant as the CSRF middleware's,
   not a second copy that drifts. A stale `?token=` URL must 400, not
   silently fall back to cookie auth without the Origin check.
